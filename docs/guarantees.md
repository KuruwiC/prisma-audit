# Audit guarantees

What the audit guarantees, and what it does not, in three separate properties: atomicity, accuracy under concurrent writes, and coverage. This document is the reference for them.

It has two layers, which follow the package boundary:

- [Core contract (@kuruwic/db-audit-core)](#core-contract-kuruwicdb-audit-core) holds what every adapter shares, in the core's terms and the database's.
- One section per adapter applies the core contract to that adapter's operations and options. Its tables cite, row by row, the tests that pin each statement down.

| Adapter | Section |
| --- | --- |
| `@kuruwic/prisma-audit`, for Prisma 6.16–7.x | [Prisma 6.16–7.x extension (@kuruwic/prisma-audit)](#prisma-6167x-extension-kuruwicprisma-audit) |
| `@kuruwic/audit-adapter-memory`, a private in-memory adapter | Follows the core contract, and has no isolation levels; no section of its own |

`scripts/check-guarantees.mjs` checks that every row of the adapter tables cites a test, that each cited file exists, and that it declares a test of the cited title that is not skipped. It checks the references only: whether a test proves the row that cites it is for review to judge.

## Core contract (@kuruwic/db-audit-core)

### Three properties

- **Atomicity**: the data a write changes and its audit rows commit together or roll back together.
- **Accuracy**: an audit row's before state, after state and action describe the change that happened, and the write it is recorded for wrote that row. This document uses the word only for writes that run concurrently with other writes.
- **Coverage**: every change to an audited model is recorded, except the ones the configuration leaves out on purpose.

Which settings give which:

- The `atomic` write mode gives atomicity: the write commits only together with every audit row it should produce. An atomic write runs inside a transaction the adapter owns, one the caller opened through the adapter or one the adapter opens around the write when none is active, and its audit rows are written in that transaction before it commits (the `immediate` write plan). When that write of the audit rows fails, the write fails with the original error and the transaction does not commit the data without them: the adapter cannot tell whether a transaction survives a failed statement (PostgreSQL aborts it, and InnoDB rolls a whole transaction back on a deadlock), so it never lets the write continue. A failure that drops a record of the write (see [Coverage](#coverage)) fails it with `AuditIncompleteError` once the observer has been notified, and the transaction rolls back. An atomic write that would run outside any transaction the adapter owns is rejected with `AuditAtomicityError` before it runs. "Every audit row" means every record was passed to the writer and the writer resolved: a custom writer that resolves without persisting the records is not detected.
- The `awaited` write mode gives atomicity inside a transaction the adapter owns, by the same `immediate` write plan, and writes the audit rows once the write has committed outside one (`awaited-after-commit`). The `deferred` write mode writes them after the commit: `after-commit` inside a transaction, `detached` outside one. Under both, a failure that drops a record is reported only. Every write plan but `immediate` writes the audit rows after the data has committed: a failure or a crash in between leaves the data without its audit rows.
- The isolation level, row locks and an optimistic-lock version column give accuracy. A transaction alone does not, the one the adapter opens for an atomic write included: atomicity and accuracy are independent, and the isolation level is the caller's choice. See [Accuracy under concurrent writes](#accuracy-under-concurrent-writes).
- The audit context, the entity map and `requireContext` decide coverage: see [Coverage](#coverage).

Three functions decide what happens to a write:

- The audit gate (`auditGate`) decides coverage: whether the write goes through the audit at all. It takes the audit context set for the write, if any, and the audited models whose rows the write writes, and returns `audit` (with that context), `skip` or `reject`. Whether a write is audited is decided by the models it writes rows of, not by the model it is issued against: a write that writes rows of an audited model is audited even when it is issued against a model that is not. The adapter derives those models and calls the gate on the arguments the write runs with, every time.
- The write policy (`policy`) decides how the audit rows of a write the gate audits are written: its write mode, the strongest (`atomic`, then `awaited`, then `deferred`) of the modes of the audited models it writes rows of, from a mode for every model or a function called once per model.
- `planFor` turns the write mode, and whether the write runs inside a transaction the adapter owns, into the write plan, or into `reject` for an atomic write outside one. The adapter calls `policy` before the write runs, so that it can open a transaction around an atomic write when none is active.

### Accuracy under concurrent writes

An adapter reads the before state of a write, and the rows a write by a condition will touch, ahead of the write, with a separate statement. Another transaction can commit a write between that read and the write. What the write then does is the database's, and it decides whether the audit row is accurate.

The table below is for a read and a write that run in the same transaction. Without a transaction, the read and the write are separate statements in separate transactions, and a commit between them is applied by the write on every database and at every isolation level: the before state is the row as read, without that commit.

| Database, isolation level | Read a row, then update it | Read no row, then insert it | Read the rows a condition matches, then update or delete by that condition |
| --- | --- | --- | --- |
| PostgreSQL, READ COMMITTED (default) | The `UPDATE` waits for the other writer, then applies to the row as the other writer committed it ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). No error: the before state lacks the other commit. | `INSERT ... ON CONFLICT DO UPDATE` updates the row the other transaction inserted, although the read found none ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). | Each statement sees the rows committed before it starts, and an `UPDATE` or `DELETE` checks its condition again against a row another writer changed ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). It writes rows inserted into, or moved into, the condition after the read, skips rows moved out of it, and does not delete a row another transaction deleted first. |
| PostgreSQL, REPEATABLE READ or SERIALIZABLE | The transaction is aborted with a serialization failure, SQLSTATE 40001, when the other transaction changed the row after the transaction's snapshot ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)). Nothing inaccurate is recorded; the application retries the transaction. | The documentation does not state what `INSERT ... ON CONFLICT DO UPDATE` does against a row inserted after the snapshot. The adapter tests observe the transaction aborted with SQLSTATE 40001. | The `UPDATE` or `DELETE` sees the transaction's snapshot: rows inserted after it are not written, and a row another transaction changed or deleted after it aborts the transaction with SQLSTATE 40001 ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)). SERIALIZABLE also aborts transactions whose reads and writes cannot be ordered ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE)). |
| MySQL (InnoDB), REPEATABLE READ (default) | The `SELECT` reads the snapshot taken by the transaction's first read; the `UPDATE` applies to the latest committed row ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)). No error: the before state lacks the other commit. | A plain `INSERT` after a `SELECT` that found no row fails on the duplicate key, error 1062 (`ER_DUP_ENTRY`, [docs](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html)). | The `UPDATE` or `DELETE` writes the latest committed rows its condition matches, rows committed after the snapshot included ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)). |

Two more cases have no row above, because no test pins them down:

- MySQL at SERIALIZABLE: InnoDB turns the plain `SELECT` of a transaction into `SELECT ... FOR SHARE` ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)), so the read ahead of the write takes a shared lock. A write of another transaction to the rows read then waits and is ordered after the transaction, or one of the two is aborted with a deadlock, error 1213 ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)). Either way no inaccurate audit row is left.
- SQLite: one connection writes at a time ([docs](https://www.sqlite.org/isolation.html)). Inside a transaction, a write is either recorded accurately or fails because another connection wrote first.

#### How to get accurate before states

These are means at the database level; the library does not apply any of them for you.

- **Optimistic lock**: give the table a version column that every writer advances, and put it in the condition of the write. When the adapter reads the before state with the same condition as the write, and both the read and the write match, no write that advances the version ran between them, so no write changed the row. A condition on another column (a compare-and-set on the column the write changes, for example) detects only writes to that column: another writer's change to any other column still lands between the read and the write.
- **Row lock**: in the same transaction, run `SELECT ... FOR UPDATE` on the row before the write ([PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [MySQL](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)). Another writer of the row waits until the transaction ends.
- **Isolation level**: on PostgreSQL, REPEATABLE READ or SERIALIZABLE, retrying a transaction that fails with SQLSTATE 40001. On MySQL, REPEATABLE READ is not enough; SERIALIZABLE is, retrying a transaction aborted with a deadlock (error 1213).

The library takes no row lock itself. A lock it took would change the order in which the application's transactions lock rows, and could deadlock transactions that are correct without it. Which rows to lock, and in what order, is the application's decision.

### Coverage

- Whether a write is audited is decided per model it writes rows of: the audited models among them are the gate's input.
- No audit context: by default the write runs unaudited. With `requireContext` holding for one of the audited models the write writes rows of, the adapter rejects the write with `AuditContextMissingError` before any of it runs.
- Writes that do not go through the adapter, such as another application's or SQL run by hand, are not recorded, and `requireContext` does not apply to them.
- Writes the database makes itself are not seen by the adapter: rows a referential action (`ON DELETE CASCADE`, `ON DELETE SET NULL` and the `ON UPDATE` ones) removes or changes, and rows a trigger writes.
- Failures reported to the observer that drop records: `row-identification` (the adapter could not identify a row the write wrote, and skips its record), `id-resolver-call` (a resolver failed, and the row loses its record, or its record under that root), and a `pre-fetch` failure of a read that decides a record's action, whose record the adapter skips. Under `atomic` such a failure fails the write with `AuditIncompleteError` and its transaction rolls back, so the write does not commit without the record; under `awaited` and `deferred` it is reported only, and the write commits without the record. A record whose before state could not be read is not a dropped record and does not fail an atomic write.
- Failures that drop records after the data has committed: `diff-generation` for a write outside any transaction (an `awaited` or `deferred` one), whose records are built once its data has committed: failing the write would invite a retry that writes it twice, so the records are dropped. A `log-write` failure under any write plan but `immediate` also leaves the write without its audit rows; under `immediate` it fails the write instead.

### Exceptions

The combinations of an operation and an execution context that change what the tables say:

- An `updateMany` or `deleteMany` with a `limit` tops up a short round only inside an interactive transaction (yours, a batch's, or the one the client opens for an atomic operation). Outside one (an awaited or deferred operation outside your transaction) it runs one narrowed statement, and under contention its count can be lower than a plain operation's. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "writes one narrowed statement outside any transaction, without topping up a round another writer left short"
- An `updateMany` or `deleteMany` with a `limit` inside a batch `$transaction([...])` reads its rows after the batch's earlier operations have run, and runs narrowed to them like inside your transaction. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "narrows the caller's updateMany inside a batch $transaction to the rows it reads after the batch's earlier operations, and audits them"
- On PostgreSQL, a before-state read that fails in the database inside a transaction (yours, a batch's, or the one the client opens for an atomic operation) aborts that transaction, so the operation fails and rolls back. Outside a transaction (an awaited or deferred operation outside yours) the operation runs, and its record has `beforeUnavailable: true`. [`before-state-read-aborts-transaction.integration.spec.ts`](../packages/integration-tests/test/before-state-read-aborts-transaction.integration.spec.ts): "fails the caller's update and rolls it back, $scope"
- The client decides whether to open a transaction around a single operation from the arguments the call is made with, and the audit decides the operation's mode again from the arguments that reach it; a batch `$transaction([...])` holding a model write runs as an interactive transaction whatever its arguments. When an extension applied before the audit (to the client passed to `createAuditClient`) adds a nested write of an atomic model to a call that its own arguments do not make atomic, the client opens no transaction, and the operation is rejected with `AuditAtomicityError` (exported by the package) before it runs: it would commit without its audit rows. [`per-model-write-policy.integration.spec.ts`](../packages/integration-tests/test/per-model-write-policy.integration.spec.ts): "rejects with AuditAtomicityError, before the write, an operation an extension applied before the audit gives a nested write of an atomic model"
- Under `atomic`, a failure that drops a record fails the operation with `AuditIncompleteError` (exported by the package; `modelName`, `operation`, and `failures`, which is also its `cause`) once the observer has been notified, and its transaction rolls back: `row-identification`, `id-resolver-call`, and a `pre-fetch` failure that skips an `upsert` or `connectOrCreate` entry, top-level or nested. A record written with `beforeUnavailable: true` is not dropped and does not fail the operation. Under `awaited` and `deferred` these failures are reported only and the operation commits. Under concurrent writes, an operation that commits and reports a missing record under `awaited` therefore fails under `atomic`, and can be retried: an `updateMany` or `deleteMany` whose `where` another writer changed at READ COMMITTED, a `createMany` with `skipDuplicates` whose count check did not match. [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "fails with AuditIncompleteError carrying the failure and rolls the write back outside any transaction", [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "commits under awaited, only reporting the rows it cannot identify", [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "fails an upsert, whose action the read decides, with AuditIncompleteError and rolls it back", [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "commits an update, recording it without its before state, which is not a dropped record", [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "id-resolver-call: fails a create whose entity idResolver throws with AuditIncompleteError and rolls it back"
- An audited write that reaches the audit without the binding the client it was issued on gives it, as an operation of a batch Prisma runs itself would, is rejected with `AuditUnboundWriteError` (exported by the package) before it runs: no audit read or write could join it. Prisma runs only batches of reads and raw queries itself, so this takes a write the client did not see as one. [`extension.spec.ts`](../packages/prisma-extension/test/extension.spec.ts): "rejects an audited write that reaches the hook as part of a batch Prisma runs, before it runs"

The transaction the client opens for an atomic operation gives atomicity only. It runs at the client's default isolation level, so a commit between the audit's read and the write is recorded as in the rows above. For a stronger isolation level, run the operation in your own `$transaction(fn, { isolationLevel })` and retry it on `P2034` yourself.

What the application can add, at READ COMMITTED:

- A version column every writer advances, in the `where` of a top-level `update` or `delete`: the audit's read ahead of the write uses the same `where`, so when the operation succeeds its before state is exact, and a write that advances the version in between makes the operation fail with `P2025` (no row matched), recording nothing. Reads after the write are separate statements too. A row a nested write updated or inserted that your own `include` / `select` leaves out, a row a nested `connect`, `set` or `disconnect` re-linked, the rows an `updateMany` wrote and the rows a `createMany` created are read again after the write, on the same client, and so are the fields an entity lists in `recordOmittedFields`. Outside a transaction such a read can see another writer's change made after the write, and a row another writer deletes, or gives another key, before the read again of the rows an `updateMany` wrote is not recorded and is reported as `row-identification`.

#### Nested to-many creates whose keys are not known before the write

A nested to-many `create` tells the rows it created by the keys the extension generates for them, so a child another transaction commits below the same parent is not taken for one of them. When the extension does not generate the key of a created row (the caller gives it; an `autoincrement()` or other database-generated key; a key field the relation fills from the parent row), or a `createMany` with `skipDuplicates` may skip a row whose key was generated, the rows are told apart by comparing the relation after the write with the row keys read ahead of it instead. A child another transaction commits below the same parent between that read and the write is then recorded as created by the nested create, although the operation did not write it. Nothing reports it.

### Coverage of Prisma writes

- A model not in `entities` is not audited. A write issued against one still records the audited rows its nested writes write. - No audit context: the write runs unaudited by default. With `requireContext`, it is rejected with `AuditContextMissingError` before Prisma runs any of it, nested writes, the transaction the client opens for an atomic operation and batch `$transaction([...])` included. [`crud.integration.spec.ts`](../packages/integration-tests/test/crud.integration.spec.ts): "should not create audit log when context is not set", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects a %s with AuditContextMissingError, leaving the database unchanged", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects without an audit context a user.create whose nested create writes a Post, requireContext holding for Post only and entities holding %s, leaving the database unchanged", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects without an audit context a batch $transaction([...]) whose second operation writes a model it holds for, leaving the database unchanged (write mode: %s)"
- `write.mode`, as a function, is called once per audited model (one in `entities`) the operation's arguments write rows of, nested writes included, and the strongest mode (`atomic`, then `awaited`, then `deferred`) applies to the whole operation: a nested write of an atomic model makes an operation of a deferred model atomic. It is called by the client before the call runs, from the call's arguments, to decide whether to open a transaction, and again by the audit from the arguments that reach it, after the extensions applied before the audit; it is not called for a read. [`per-model-write-policy.integration.spec.ts`](../packages/integration-tests/test/per-model-write-policy.integration.spec.ts): "is called once per audited model the operation writes, and a nested atomic model makes a deferred top-level operation atomic", [`per-model-write-policy.integration.spec.ts`](../packages/integration-tests/test/per-model-write-policy.integration.spec.ts): "is not called for a read operation"
- The audit covers the arguments that reach it. A write an extension applied after the audit (to the audited client, `createAuditClient(...).$extends(...)`) adds to an operation's arguments runs later than the audit: it is neither recorded nor rejected by `requireContext`. Apply an extension that changes arguments to the client you pass to `createAuditClient`. [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "runs without an audit context a user.update to which an extension applied after the audit adds a nested Post create, requireContext holding for Post"
- `$executeRaw`, `$queryRaw` and their `Unsafe` variants have no model, and the audit extension does not see them.
- A model identified by a unique field instead of a primary key (`@unique` or `@@unique` on required fields, no `@id` or `@@id`) is audited like a model with one, nested writes included: its rows are told apart by that unique constraint, its row key, wherever the rows of other models are told apart by their primary key. A nested `create`, `createMany`, `update`, `upsert`, `delete`, `updateMany`, `deleteMany`, `connect`, `disconnect`, `set` or `connectOrCreate` into such a model, and the writes nested below one of its rows, record one log per row they write, as they do for a model with a primary key; so do top-level batch operations. - A nested `update`, the update branch of a nested `upsert` and a nested `updateMany` that give the rows they write another row key, primary key or unique key, record each row under the key the write gives it, which is the key it had with the key fields the data gives literal values replaced. A key the data changes in a way its arguments do not tell (an operator on a key field) is reported as `row-identification`, and the row is not recorded. - A row key that holds the foreign key to the parent row holds after the write the parent's referenced columns as they are after the write. A row a nested `connect` moves in from another parent is recorded once, as the change of that foreign key, under the key it has under the new parent, and not as created; a row a nested `updateMany` writes below a parent whose referenced column the same operation changes, and a row a nested `update` or the update branch of a nested `upsert` names there by the parent's new value, is recorded under the key `ON UPDATE CASCADE` gives it, with the before state it had under the parent's old value and the foreign-key change in its `changes`; a row that change re-keys without a nested write naming it is not recorded as created. - Writes at one relation path that their keys after the write cannot tell apart, targets naming different rows that end up with the same key and a target naming the key another target's write gives a row, are reported as `row-identification` and not recorded, so no record pairs a row with another row's before state. At a path holding a row whose key after the write is unknown, the rows inserted there without a key the extension generated are not recorded either and are reported as `row-identification` per inserting operation; rows with a key the extension generated are recorded. - A write through a client without the audit extension, such as the client passed to `createAuditClient` or another `PrismaClient`, is not audited, and `requireContext` does not apply to it.
- Rows a referential action (`onDelete` / `onUpdate`, such as `Cascade` or `SetNull`) removes or changes are not audited: the database writes them without a Prisma query. Deleting a `Post` whose `Comment` rows cascade records the `Post` and none of its comments, and a row `SetNull` clears the foreign key of has no record of that change. A row a nested write of the same operation also writes is recorded for that write, and its record carries the change the referential action made with the rest (see the row key that holds the foreign key to the parent row, above). [`nested-delete.integration.spec.ts`](../packages/integration-tests/test/nested-delete.integration.spec.ts): "audits the deleted post and does not audit the comments the database cascades the delete to"
- `connect`, `set` and `disconnect` on an implicit many-to-many relation (no relation model, such as `categories Category[]` on both sides) change rows of Prisma's join table, which has no model: they are not audited. [`nested-link-changes.integration.spec.ts`](../packages/integration-tests/test/nested-link-changes.integration.spec.ts): "audits nothing for a connect through an implicit many-to-many relation"
- A write issued while the audit processes an operation, such as one a user callback (`idResolver`, an enricher, a serializer) makes through the audited client, is not audited, so that the audit does not recurse; `requireContext` does not apply to it. [`extension.spec.ts`](../packages/prisma-extension/test/extension.spec.ts): "runs unaudited a write issued while the audit processes an operation, such as one of a user callback's, without a context"
- `updateMany` and `deleteMany` read their rows ahead of the write, so a row another transaction moves into or out of the `where`, or deletes first, in between is missed or recorded wrongly (see [Accuracy](#accuracy-of-prisma-operations-under-concurrent-writes)). A count above the rows read, or below the read rows found again after the write, is reported as `row-identification`, which fails an atomic operation (see [Exceptions](#exceptions)); a swap that keeps the count is not seen.
- An `upsert`, top-level or nested, whose before-state read failed is not recorded, together with the writes of its branches, since the read decides its action (reported as `pre-fetch`). Under `atomic` the operation then fails with `AuditIncompleteError` and rolls back; under `awaited` and `deferred` it runs without the entry. [`atomic-incomplete.integration.spec.ts`](../packages/integration-tests/test/atomic-incomplete.integration.spec.ts): "fails an upsert, whose action the read decides, with AuditIncompleteError and rolls it back", [`top-level-upsert-nested.integration.spec.ts`](../packages/integration-tests/test/top-level-upsert-nested.integration.spec.ts): "skips the nested entries of an upsert whose before-state fetch failed, and the caller still succeeds"
- Outside any transaction (an awaited or deferred operation outside yours), a failure to build the records after the write drops them (reported as `diff-generation`). [`transaction-mode.integration.spec.ts`](../packages/integration-tests/test/transaction-mode.integration.spec.ts): "keeps a committed write whose awaited audit build failed, and reports the dropped records"
- Gaps that depend on how nested writes are written (the order of the keywords of one relation field, a `connectOrCreate` and a `delete` of the same row, `fetchBefore.update` off for `connect`, `set` and `disconnect`) are described under [Nested Operations limitations](../packages/prisma-extension/README.md#limitations).
