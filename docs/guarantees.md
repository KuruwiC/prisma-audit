# Audit guarantees

What the audit guarantees, and what it does not, in three separate properties: atomicity, accuracy under concurrent writes, and coverage. This document is the reference for them; the READMEs link here.

It has two layers, which follow the package boundary:

- [Core contract (@kuruwic/db-audit-core)](#core-contract-kuruwicdb-audit-core) holds what every adapter shares, in the core's terms and the database's.
- One section per adapter applies the core contract to that adapter's operations and options. Its tables cite, row by row, the tests that pin each statement down.

| Adapter | Section |
| --- | --- |
| `@kuruwic/prisma-audit`, for Prisma 6.16–7.x | [Prisma 6.16–7.x extension (@kuruwic/prisma-audit)](#prisma-6167x-extension-kuruwicprisma-audit) |
| `@kuruwic/audit-adapter-memory`, a private in-memory adapter | Follows the core contract, and has no isolation levels; no section of its own |

`scripts/check-guarantees.mjs` checks that every row of the adapter tables cites a test, that each cited file exists, and that it declares a test of the cited title that is not skipped. It checks the references only: whether a test proves the row that cites it is for review to judge.

## Core contract (@kuruwic/db-audit-core)

### Three properties

- **Atomicity**: the data a write changes and its audit rows commit together or roll back together.
- **Accuracy**: an audit row's before state, after state and action describe the change that happened, and the write it is recorded for wrote that row. This document uses the word only for writes that run concurrently with other writes.
- **Coverage**: every change to an audited model is recorded, except the ones the configuration leaves out on purpose.

Which settings give which:

- `awaited` and a transaction give atomicity. An awaited write inside a transaction writes its audit rows in that transaction, before it commits (the `immediate` write plan). Every other write plan (`awaited-after-commit`, `after-commit`, `detached`) writes them after the data has committed: a failure or a crash in between leaves the data without its audit rows.
- The isolation level, row locks and an optimistic-lock version column give accuracy. A transaction alone does not: see [Accuracy under concurrent writes](#accuracy-under-concurrent-writes).
- The audit context, `samplingRate` and `requireContext` decide coverage: see [Coverage](#coverage).

Two functions decide what happens to a write, and they answer different questions:

- The audit gate (`auditGate`) decides coverage: whether the write goes through the audit at all. It takes whether an audit context is set and the audited models whose rows the write writes, and returns `audit`, `skip` or `reject`. Whether a write is audited is decided by the models it writes rows of, not by the model it is issued against: a write that writes rows of an audited model is audited even when it is issued against a model that is not. The adapter derives those models and calls the gate on the arguments the write runs with, every time.
- The write policy (`policy`) decides how much of what the gate audits is recorded, and how: whether the write is sampled in (`samplingRate`), and whether its audit rows are written atomically with it (`awaited`, which gives `atomic`).

### Accuracy under concurrent writes

An adapter reads the before state of a write, and the rows a write by a condition will touch, ahead of the write, with a separate statement. Another transaction can commit a write between that read and the write. What the write then does is the database's, and it decides whether the audit row is accurate.

The table below is for a read and a write that run in the same transaction. Without a transaction, the read and the write are separate statements in separate transactions, and a commit between them is applied by the write on every database and at every isolation level: the before state is the row as read, without that commit.

| Database, isolation level | Read a row, then update it | Read no row, then insert it | Read the rows a condition matches, then update or delete by that condition |
| --- | --- | --- | --- |
| PostgreSQL, READ COMMITTED (default) | The `UPDATE` waits for the other writer, then applies to the row as the other writer committed it ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). No error: the before state lacks the other commit. | `INSERT ... ON CONFLICT DO UPDATE` updates the row the other transaction inserted, although the read found none ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). | Each statement sees the rows committed before it starts, and an `UPDATE` or `DELETE` checks its condition again against a row another writer changed ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). It writes rows inserted into, or moved into, the condition after the read, skips rows moved out of it, and does not delete a row another transaction deleted first. |
| PostgreSQL, REPEATABLE READ or SERIALIZABLE | The transaction is aborted with a serialization failure, SQLSTATE 40001, when the other transaction changed the row after the transaction's snapshot ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)). Nothing inaccurate is recorded; the application retries the transaction. | The documentation does not state what `INSERT ... ON CONFLICT DO UPDATE` does against a row inserted after the snapshot. The adapter tests observe the transaction aborted with SQLSTATE 40001. | The `UPDATE` or `DELETE` sees the transaction's snapshot: rows inserted after it are not written, and a row another transaction changed or deleted after it aborts the transaction with SQLSTATE 40001 ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)). SERIALIZABLE also aborts transactions whose reads and writes cannot be ordered ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE)). |
| MySQL (InnoDB), REPEATABLE READ (default) | The `SELECT` reads the snapshot taken by the transaction's first read; the `UPDATE` applies to the latest committed row ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)). No error: the before state lacks the other commit. | A plain `INSERT` after a `SELECT` that found no row fails on the duplicate key, error 1062 (`ER_DUP_ENTRY`, [docs](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html)). | The `UPDATE` or `DELETE` writes the latest committed rows its condition matches, rows committed after the snapshot included ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)). |

Two more cases have no row above, because no test pins them down:

- MySQL at SERIALIZABLE: InnoDB turns the plain `SELECT` of a transaction into `SELECT ... FOR SHARE` ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)), so the read ahead of the write takes a shared lock. A write of another transaction to the rows read then waits and is ordered after the transaction, or one of the two is aborted with a deadlock, error 1213 ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)). Either way no inaccurate audit row is left.
- SQLite: one connection writes at a time ([docs](https://www.sqlite.org/isolation.html)). Inside a transaction, a write is either recorded accurately or fails because another connection wrote first.

#### How to get accurate before states

These are means at the database level; the library does not apply any of them for you.

- **Optimistic lock**: give the table a version column that every writer advances, and put it in the condition of the write. When the adapter reads the before state with the same condition as the write, and both the read and the write match, no write that advances the version ran between them, so no write changed the row. A condition on another column (a compare-and-set on the column the write changes, for example) detects only writes to that column: another writer's change to any other column still lands between the read and the write.
- **Row lock**: in the same transaction, run `SELECT ... FOR UPDATE` on the row before the write ([PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [MySQL](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)). Another writer of the row waits until the transaction ends.
- **Isolation level**: on PostgreSQL, REPEATABLE READ or SERIALIZABLE, retrying a transaction that fails with SQLSTATE 40001. On MySQL, REPEATABLE READ is not enough; SERIALIZABLE is, retrying a transaction aborted with a deadlock (error 1213).

The library takes no row lock itself. A lock it took would change the order in which the application's transactions lock rows, and could deadlock transactions that are correct without it. Which rows to lock, and in what order, is the application's decision.

### Coverage

- Whether a write is audited is decided per model it writes rows of: the audited models among them are the gate's input.
- No audit context: by default the write runs unaudited. With `requireContext` holding for one of the audited models the write writes rows of, the adapter rejects the write with `AuditContextMissingError` before any of it runs.
- Sampling: a write `samplingRate` leaves out is not recorded. This is a declared gap. `requireContext` does not depend on sampling: a write without an audit context is rejected at a `samplingRate` of 0 as well.
- Writes that do not go through the adapter, such as another application's or SQL run by hand, are not recorded, and `requireContext` does not apply to them.
- Writes the database makes itself are not seen by the adapter: rows a referential action (`ON DELETE CASCADE`, `ON DELETE SET NULL` and the `ON UPDATE` ones) removes or changes, and rows a trigger writes.
- Failures reported to the observer that drop records: `row-identification` (the adapter could not identify a row the write wrote, and skips its record), `id-resolver-call` (a resolver failed, and the row loses its record, or its record under that root), and for a detached write `diff-generation` and `log-write`, since the data has committed and the caller has its result. A `log-write` failure the write-failure policy does not rethrow also leaves the write without its audit rows. An adapter may drop the records of a committed write in other cases; its section says when.

### Exceptions

The combinations of an operation and an execution context that change what the tables say:

- An `updateMany` or `deleteMany` with a `limit` inside a batch `$transaction([...])` that Prisma runs itself runs as given, with its `limit`: a read ahead of it could not see what the batch's earlier operations wrote. None of its rows is recorded, and their number is reported as `row-identification`. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "continues the caller's updateMany unchanged inside a batch Prisma runs, and reports its rows as row-identification"
- An `updateMany` or `deleteMany` with a `limit` tops up a short round only inside an interactive transaction (yours, or the one `write.implicitTransaction` opens). Outside one it runs one narrowed statement, and under contention its count can be lower than a plain operation's. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "writes one narrowed statement outside any transaction, without topping up a round another writer left short"
- A `createMany` inside a batch `$transaction([...])` that Prisma runs itself is read back after the whole batch: a row a later operation of the batch deletes is not recorded. [`crud.integration.spec.ts`](../packages/integration-tests/test/crud.integration.spec.ts): "records no create of a row a later operation of the same batch $transaction deleted"
- On PostgreSQL, a before-state read that fails in the database inside a transaction (yours, or the one `write.implicitTransaction` opens) aborts that transaction, so the operation fails and rolls back. Outside a transaction the operation runs, and its record has `beforeUnavailable: true`. [`before-state-read-aborts-transaction.integration.spec.ts`](../packages/integration-tests/test/before-state-read-aborts-transaction.integration.spec.ts): "fails the caller's update and rolls it back, $scope"
- `write.implicitTransaction` decides whether to open a transaction from the arguments the call is made with. When an extension applied before the audit (to the client passed to `createAuditClient`) adds a nested write of an audited model to them, no transaction opens, and an awaited audit is written once the operation has committed.

`write.implicitTransaction` gives atomicity only. The transaction it opens runs at the client's default isolation level, so a commit between the audit's read and the write is recorded as in the rows above. For a stronger isolation level, run the operation in your own `$transaction(fn, { isolationLevel })` and retry it on `P2034` yourself.

What the application can add, at READ COMMITTED:

- A version column every writer advances, in the `where` of a top-level `update` or `delete`: the audit's read ahead of the write uses the same `where`, so when the operation succeeds its before state is exact, and a write that advances the version in between makes the operation fail with `P2025` (no row matched), recording nothing. The tests cover a top-level `update`; no test covers a nested write guarded this way. [`concurrent-write.postgresql.spec.ts`](../packages/integration-tests/test/concurrency/concurrent-write.postgresql.spec.ts): "rejects an update guarded by a version column every writer advances when another transaction advances it between the read and the update, recording nothing", [`concurrent-write.postgresql.spec.ts`](../packages/integration-tests/test/concurrency/concurrent-write.postgresql.spec.ts): "records the exact before state of an update guarded by a version column when no other transaction writes the row"
- `SELECT ... FOR UPDATE` through `$queryRaw` in your transaction before the write: the other writer waits until your transaction commits, so the row the audit reads is the row your write changes. [`concurrent-write.postgresql.spec.ts`](../packages/integration-tests/test/concurrency/concurrent-write.postgresql.spec.ts): "records the before state of an update whose row the transaction locked with SELECT ... FOR UPDATE, and the other writer applies its change after the transaction commits"

Reads after the write are separate statements too. A row a nested write updated or inserted that your own `include` / `select` leaves out, a row a nested `connect`, `set` or `disconnect` re-linked, the rows an `updateMany` wrote and the rows a `createMany` created are read again after the write, on the same client, and so are the fields an entity lists in `recordOmittedFields`. Outside a transaction such a read can see another writer's change made after the write.

#### Nested to-many creates: a known defect

A nested to-many `create` tells the rows it created from the rows the relation already held by comparing the relation after the write with the primary keys read ahead of it. A child another transaction commits below the same parent in between is therefore recorded as created by the nested create, although the operation did not write it. Nothing reports it.

A possible fix, not implemented: identify each created row by a key the operation itself knows, instead of by what appeared. That key can come from three places: the caller passes it in `data`; the extension generates it client-side, as it does for `createMany`, when the schema gives the key a `cuid()` or `uuid()` default; or nothing gives it before the write (an `autoincrement()` or other database-generated key), in which case the defect stays.

### Coverage of Prisma writes

- A model not in `entities` is not audited. A write issued against one still records the audited rows its nested writes write. [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "records the Post a nested create of a user.create writes, and not the User, when entities hold Post and not User"
- No audit context: the write runs unaudited by default. With `requireContext`, it is rejected with `AuditContextMissingError` before Prisma runs any of it, nested writes, `write.implicitTransaction` and batch `$transaction([...])` included, whatever `samplingRate` says. [`crud.integration.spec.ts`](../packages/integration-tests/test/crud.integration.spec.ts): "should not create audit log when context is not set", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects a %s with AuditContextMissingError, leaving the database unchanged", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects without an audit context a user.create whose nested create writes a Post, requireContext holding for Post only and entities holding %s, leaving the database unchanged", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects without an audit context a batch $transaction([...]) whose second operation writes a model it holds for, leaving the database unchanged (implicitTransaction: %s)", [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "rejects without an audit context a write of a model it holds for at a samplingRate of 0"
- `samplingRate` and `write.awaited` are decided by the operation's top-level model, and its nested writes follow that decision whatever their own model would get. [`per-model-write-policy.integration.spec.ts`](../packages/integration-tests/test/per-model-write-policy.integration.spec.ts): "skips the nested writes of a top-level model whose rate is 0, whatever their own model would get", [`per-model-write-policy.integration.spec.ts`](../packages/integration-tests/test/per-model-write-policy.integration.spec.ts): "does not await the nested writes of a top-level model it does not await, whatever their own model would get"
- The audit covers the arguments that reach it. A write an extension applied after the audit (to the audited client, `createAuditClient(...).$extends(...)`) adds to an operation's arguments runs later than the audit: it is neither recorded nor rejected by `requireContext`. Apply an extension that changes arguments to the client you pass to `createAuditClient`. [`require-context.integration.spec.ts`](../packages/integration-tests/test/require-context.integration.spec.ts): "runs without an audit context a user.update to which an extension applied after the audit adds a nested Post create, requireContext holding for Post"
- `$executeRaw`, `$queryRaw` and their `Unsafe` variants have no model, and the audit extension does not see them.
- A write through a client without the audit extension, such as the client passed to `createAuditClient` or another `PrismaClient`, is not audited, and `requireContext` does not apply to it.
- Rows a referential action (`onDelete` / `onUpdate`, such as `Cascade` or `SetNull`) removes or changes are not audited: the database writes them without a Prisma query. Deleting a `Post` whose `Comment` rows cascade records the `Post` and none of its comments, and a row `SetNull` clears the foreign key of has no record of that change. [`nested-delete.integration.spec.ts`](../packages/integration-tests/test/nested-delete.integration.spec.ts): "audits the deleted post and does not audit the comments the database cascades the delete to"
- `connect`, `set` and `disconnect` on an implicit many-to-many relation (no relation model, such as `categories Category[]` on both sides) change rows of Prisma's join table, which has no model: they are not audited. [`nested-link-changes.integration.spec.ts`](../packages/integration-tests/test/nested-link-changes.integration.spec.ts): "audits nothing for a connect through an implicit many-to-many relation"
- A write issued while the audit processes an operation, such as one a user callback (`idResolver`, an enricher, a serializer) makes through the audited client, is not audited, so that the audit does not recurse; `requireContext` does not apply to it. [`extension.spec.ts`](../packages/prisma-extension/test/extension.spec.ts): "runs unaudited a write issued while the audit processes an operation, such as one of a user callback's, without a context"
- `updateMany` and `deleteMany` read their rows ahead of the write, so a row another transaction moves into or out of the `where`, or deletes first, in between is missed or recorded wrongly (see [Accuracy](#accuracy-of-prisma-operations-under-concurrent-writes)). A count that differs from the rows read is reported as `row-identification`; a swap that keeps the count is not seen.
- An `upsert`, top-level or nested, whose before-state read failed is not recorded, together with the writes of its branches, since the read decides its action (reported as `pre-fetch`). [`top-level-upsert-nested.integration.spec.ts`](../packages/integration-tests/test/top-level-upsert-nested.integration.spec.ts): "skips the nested entries of an upsert whose before-state fetch failed, and the caller still succeeds"
- Outside any transaction, a failure to build the records after the write drops them, awaited or not (reported as `diff-generation`). [`transaction-mode.integration.spec.ts`](../packages/integration-tests/test/transaction-mode.integration.spec.ts): "keeps a committed write whose awaited audit build failed, and reports the dropped records"
- Gaps that depend on how nested writes are written (the order of the keywords of one relation field, a `connectOrCreate` and a `delete` of the same row, `fetchBefore.update` off for `connect`, `set` and `disconnect`) are described under [Nested Operations limitations](../packages/prisma-extension/README.md#limitations).
