## Core contract (@kuruwic/db-audit-core)

### Three properties

- **Atomicity**: the data a write changes and its audit rows commit together or roll back together.
- **Accuracy**: an audit row's before state, after state and action describe the change that happened, and the write it is recorded for wrote that row. Accuracy here concerns writes that run concurrently with other writes.
- **Coverage**: every change to an audited model is recorded, except the ones the configuration leaves out on purpose.

Three functions decide what happens to a write:

- The audit gate (`auditGate`) decides coverage. It takes the audit context set for the write, if any, and the audited models whose rows the write writes. It returns `audit` (with that context), `skip` for a write of no audited model, `unaudited` (reason `no-context`) for one without an audit context, or `reject`. The models a write writes rows of decide, not the model it is issued against: a write issued against an unaudited model is audited when it writes rows of an audited one. The adapter derives those models from the arguments the write runs with, every time.
- The write policy (`policy`) decides the write mode: the strongest (`atomic`, then `awaited`, then `deferred`) of the modes of the audited models the write writes rows of. A model's mode is its entity's `writeMode`, else the default mode, `atomic` unless configured.
- `planFor` turns the write mode, and whether the write runs inside a transaction the adapter owns, into the write plan:

| Write mode | Inside a transaction the adapter owns | Outside one |
| --- | --- | --- |
| `atomic` | `immediate` | `reject`: `AuditAtomicityError` before the write runs |
| `awaited` | `immediate` | `awaited-after-commit`: written once the write has committed, before it returns |
| `deferred` | `immediate` | `detached`: written after the write returns, without waiting |

The adapter calls `policy` before the write runs, so that it can open a transaction around an atomic write when none is active.

What the write plan gives:

- `immediate` gives atomicity. The audit rows are written in the transaction before the write returns, so they commit and roll back with the data they record, whatever undoes it. When that write of the audit rows fails, the write fails with the original error and the transaction does not commit: the adapter cannot tell whether a transaction survives a failed statement (PostgreSQL aborts it, and InnoDB rolls a whole transaction back on a deadlock).
- `awaited-after-commit` and `detached` write the audit rows after the data has committed. A failure or a crash in between leaves the data without its audit rows.
- A failure that drops a record (see [Coverage](#coverage)) fails an `atomic` write with `AuditIncompleteError`, and its transaction rolls back. Under `awaited` and `deferred` it is reported only.
- The transaction's audit (`TransactionAudit`) records (`poison`) each audit failure that failed a write once the write had run. Before the commit the adapter calls `assertCommittable`, and a transaction holding such a failure rolls back with `AuditRollbackError`, even when the code that ran the write caught the error. When the transaction ends, `end` settles the outcomes of its writes; a nested transaction's audit is merged into its parent's instead (`mergeInto`).
- "Every audit row" means every record was passed to the writer and the writer resolved. A custom writer that resolves without persisting the records is not detected.

The isolation level, row locks and an optimistic-lock version column give accuracy. A transaction alone does not, the one the adapter opens for an atomic write included: see [Accuracy under concurrent writes](#accuracy-under-concurrent-writes). The audit context, the entity map and `requireContext` decide coverage: see [Coverage](#coverage).

### Accuracy under concurrent writes

An adapter reads the before state of a write, and the rows a write by a condition will touch, with a separate statement ahead of the write. Another transaction can commit a write between that read and the write. What the database then does decides whether the audit row is accurate.

The table is for a read and a write in the same transaction. Without a transaction, they run in separate transactions, and the write applies a commit made between them on every database and at every isolation level: the before state is the row as read, without that commit.

| Database, isolation level | Read a row, then update it | Read no row, then insert it | Read the rows a condition matches, then update or delete by that condition |
| --- | --- | --- | --- |
| PostgreSQL, READ COMMITTED (default) | The `UPDATE` waits for the other writer, then applies to the row as the other writer committed it ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)). No error: the before state lacks the other commit. | `INSERT ... ON CONFLICT DO UPDATE` updates the row the other transaction inserted, although the read found none. | Each statement sees the rows committed before it starts, and an `UPDATE` or `DELETE` checks its condition again against a row another writer changed. It writes rows inserted into, or moved into, the condition after the read, skips rows moved out of it, and does not delete a row another transaction deleted first. |
| PostgreSQL, REPEATABLE READ or SERIALIZABLE | The transaction is aborted with a serialization failure, SQLSTATE 40001, when the other transaction changed the row after the transaction's snapshot ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)). Nothing inaccurate is recorded; the application retries the transaction. | Not stated by the PostgreSQL documentation for a row inserted after the snapshot. The adapter tests observe the transaction aborted with SQLSTATE 40001. | The `UPDATE` or `DELETE` sees the transaction's snapshot: rows inserted after it are not written, and a row another transaction changed or deleted after it aborts the transaction with SQLSTATE 40001. SERIALIZABLE also aborts transactions whose reads and writes cannot be ordered ([docs](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE)). |
| MySQL (InnoDB), REPEATABLE READ (default) | The `SELECT` reads the snapshot taken by the transaction's first read; the `UPDATE` applies to the latest committed row ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)). No error: the before state lacks the other commit. | A plain `INSERT` after a `SELECT` that found no row fails on the duplicate key, error 1062 (`ER_DUP_ENTRY`, [docs](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html)). | The `UPDATE` or `DELETE` writes the latest committed rows its condition matches, rows committed after the snapshot included. |

Two cases no test pins down:

- MySQL at SERIALIZABLE: InnoDB turns a transaction's plain `SELECT` into `SELECT ... FOR SHARE` ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)), so the read ahead of the write takes a shared lock. Another transaction's write to the rows read then waits and is ordered after the transaction, or one of the two is aborted with a deadlock, error 1213 ([docs](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)). Either way no inaccurate audit row is left.
- SQLite: one connection writes at a time ([docs](https://www.sqlite.org/isolation.html)). Inside a transaction, a write is either recorded accurately or fails because another connection wrote first.

#### How to get accurate before states

These are database-level means. The core applies none of them; an adapter may open the transaction of an atomic write at an isolation level it is configured with, and applies nothing else.

- **Optimistic lock**: give the table a version column that every writer advances, and put it in the condition of the write. When the adapter reads the before state with the same condition as the write and both match, no write changed the row in between. A condition on another column (a compare-and-set on the column the write changes, for example) detects only writes to that column.
- **Row lock**: in the same transaction, run `SELECT ... FOR UPDATE` on the row before the write ([PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [MySQL](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)). Another writer of the row waits until the transaction ends.
- **Isolation level**: on PostgreSQL, REPEATABLE READ or SERIALIZABLE, retrying a transaction that fails with SQLSTATE 40001. On MySQL, SERIALIZABLE (REPEATABLE READ is not enough), retrying a transaction aborted with a deadlock (error 1213).

The library retries no transaction that fails on a serialization conflict or a deadlock: whether running the transaction, and the code in it, again is safe is the caller's decision.

The library takes no row lock itself. A lock it took would change the order in which the application's transactions lock rows, and could deadlock transactions that are correct without it. Which rows to lock, and in what order, is the application's decision.

### Coverage

- Whether a write is audited is decided by the audited models it writes rows of, which are the gate's input.
- No audit context: the adapter rejects the write with `AuditContextMissingError` before any of it runs when `requireContext` holds for one of the audited models it writes rows of, which it does for every model when unset. When it holds for none of them, the write runs unaudited. [`audit-gate.spec.ts`](../packages/db-audit-core/test/audit-gate.spec.ts): "rejects a write without an audit context, requireContext %s, naming the first model", [`audit-gate.spec.ts`](../packages/db-audit-core/test/audit-gate.spec.ts): "runs a write without an audit context unaudited when requireContext is false", [`adapter-memory.spec.ts`](../packages/adapter-memory/test/adapter-memory.spec.ts): "rejects a write without an audit context by default, leaving the store unchanged"
- A write issued while the audit processes a write, from the audit's own work or from a callback it runs (a resolver, an enricher and its `onError`, a writer, the observer), is not the caller's write. When it writes rows of an audited model, the adapter rejects it with `AuditReentrantWriteError` before any of it runs, with or without an audit context, and it has no outcome; one of no audited model runs. The handle the adapter gives the callbacks is its audited handle, so a write through it reaches this rejection. The place the write was issued from fails or reports as it does for any other error of its own, and an enricher's `onError` does not turn the rejection into a fallback, nor any other an adapter throws for a write it rejects before it runs: every such error extends `RejectedWriteError`. An enricher that has timed out was handled by its `onError` then: the rejection of a write it issues afterwards is logged to the console.
- The models the audit rows are written to are not audited models: the adapter's own write of the records would be rejected as above. An adapter checks this, for the destinations it knows, when it is created.
- Writes that do not go through the adapter, such as another application's or SQL run by hand, are not recorded, and `requireContext` does not apply to them.
- The adapter does not see the writes the database makes itself: rows a referential action (`ON DELETE CASCADE`, `ON DELETE SET NULL` and the `ON UPDATE` ones) removes or changes, and rows a trigger writes.
- These failures drop records, and the write's [outcome](#outcome-of-a-write) reports them:
  - `row-identification`: the adapter could not identify a row the write wrote, and skips its record.
  - `id-resolver-call`: a resolver failed, and the row loses its record, or its record under that root.
  - `pre-fetch`, for a read that decides a record's action or finds the rows a write changed: the adapter skips those records. The outcome and `AuditIncompleteError` name each write left without a record (its model, keyword and path).

  Under `atomic` they fail the write with `AuditIncompleteError` and its transaction rolls back; under `awaited` and `deferred` they are reported only, and the write commits without the record. A record whose before state could not be read is not a dropped record and does not fail an atomic write.
- An enricher whose failure (an error, a timeout, or a batch result of the wrong length) its `onError` resolves to `'log'` or `'ignore'` drops no record: its `fallback`, else null, is stored in place of the context it was to enrich. The write's outcome lists it as an `enrichment` failure with the kind of the enricher (`actor`, `entity` or `aggregate`, the root-side and the projection-side aggregate enrichers alike), once per enricher call, under `'ignore'` too, which only keeps it off the console. The outcome stays `complete`, and an atomic write does not fail. [`run-enricher.spec.ts`](../packages/db-audit-core/test/enrichment/run-enricher.spec.ts): "reports the error a single-row and a batch enricher fall back on, onError %s", [`resolve.spec.ts`](../packages/db-audit-core/test/resolve.spec.ts): "reports an actor enricher failure to the sink as an actor enrichment failure", [`resolve.spec.ts`](../packages/db-audit-core/test/resolve.spec.ts): "reports an entity enricher failure to the sink once per model as an entity enrichment failure", [`resolve.spec.ts`](../packages/db-audit-core/test/resolve.spec.ts): "reports %s aggregate enricher failure to the sink as an aggregate enrichment failure", [`outcome.spec.ts`](../packages/db-audit-core/test/outcome.spec.ts): "is complete with the %s enrichment failure an enricher fell back on, which drops no record", [`adapter-memory.spec.ts`](../packages/adapter-memory/test/adapter-memory.spec.ts): "is complete for an atomic write whose enrichers fall back under onError '%s', listing each as an enrichment failure"
- Outside any transaction, the records are built and written after the data has committed. A `diff-generation` failure then drops the records: failing the write would invite a retry that writes it twice. A `log-write` failure leaves the write without its audit rows. Under `immediate` both fail the write instead.

### Outcome of a write

The observer is called once for every write that writes rows of an audited model, with the outcome of its audit, once the write is settled. A write of no audited model has no outcome.

| Status | Meaning |
| --- | --- |
| `complete` | The write committed, and every record it produced was passed to a writer that resolved. An atomic write that commits is always `complete`. A failure that only cost a record its before state, or a context an enricher fell back on, may be listed. It does not mean the records are accurate: the premise of accuracy is the outcome's `isolation`. |
| `incomplete` | The write committed without some of its records: a failure dropped them or left a write without a record (only under `awaited` and `deferred`), or the write of the records failed after the commit, and how many the writer persisted is not known. |
| `not-committed` | The write failed, `AuditIncompleteError`, `AuditAtomicityError` and `AuditContextMissingError` included, or the transaction it ran in rolled back or failed to commit. |
| `unaudited` | The write committed without going through the audit, for `unauditedReason` `no-context`: no audit context was set, and none was required. |

- The outcome names the operation's model and keyword, counts the records passed to a writer that resolved, and lists the audit's failures, each typed by its phase, and the writes left without a record. A `log-write` failure carries the records the write was given, so the observer can keep them elsewhere. The outcome does not count the missing records, except the rows a `row-identification` failure could not identify.
- Outside any transaction, the outcome is reported when the write returns or throws, or, for a `detached` write, once the write of its records has run. Inside a transaction the adapter owns, the outcomes of its writes are reported once it has committed, or as `not-committed` once it has rolled back: a write inside a transaction that rolls back is never reported `complete`. This includes a transaction the database aborted on a failed statement that the code running the transaction caught. Once an operation of the transaction has failed, the adapter checks before the commit that the transaction is still usable, and rolls it back when it is not. A write that finishes after its transaction has settled is reported at once.
- The outcome's `isolation` is what the adapter knows of the transaction the write's reads and the write ran in, whatever the status. The audit cannot observe whether a record is accurate, only this premise: `no-transaction` when they ran in no common transaction (outside any, under `awaited` or `deferred`, or without an audit context, so rejected or run unaudited, under any mode), `undeclared` when they ran in one at a level not declared to the adapter (the database's or the client's default), and `declared`, with the adapter's name for the level, when they ran in one opened at a declared level. What a level guarantees depends on the database: see [Accuracy under concurrent writes](#accuracy-under-concurrent-writes). The core treats the level as an opaque name and compares none. An adapter that has no isolation levels reports `no-transaction` or `undeclared` only. [`outcome.spec.ts`](../packages/db-audit-core/test/outcome.spec.ts): "carries the isolation %s the adapter gave, whatever the status", [`adapter-memory.spec.ts`](../packages/adapter-memory/test/adapter-memory.spec.ts): "is no-transaction for a %s write outside any transaction, whose read and write share none", [`adapter-memory.spec.ts`](../packages/adapter-memory/test/adapter-memory.spec.ts): "is undeclared for a %s write in a transaction and in one nested in it"
- Without an observer, the failures of an `incomplete` outcome are logged to the console, except an `enrichment` failure, which lost no record; the other outcomes are not. [`outcome.spec.ts`](../packages/db-audit-core/test/outcome.spec.ts): "does not log the enrichment failure of an incomplete outcome, which lost no record" An observer that throws or rejects is logged to the console and never affects the write.

### Redaction of stored values

- The serializers run first, then the redactor masks the built-in sensitive fields and `redactFields` in the before state, the after state, the changes and the four contexts (`actorContext`, `entityContext`, `aggregateContext` and `requestContext`). A field matches by its key, at any depth of nested objects and lists, and the serializers' conversions of the other values are kept. [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "redacts the built-in sensitive fields in before, after and changes with no redactFields configured", [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "redacts the redactFields on top of the built-in sensitive fields", [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "redacts a sensitive key inside a class instance among the column values", [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "redacts the built-in sensitive fields and redactFields at any depth", [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "redacts after serializing: a sensitive key of a class instance is masked, and BigInt and Date values are kept as strings"
- Only the keys of the structure the serializers output are masked. A serializer that turns an object into a string hides its keys from the redactor, and they are stored in clear. [`compose.spec.ts`](../packages/db-audit-core/test/compose.spec.ts): "leaves the keys inside a value a custom serializer turns into a string unredacted"

The combinations of an operation and an execution context that change what the tables say:

- An `updateMany` or `deleteMany` with a `limit` tops up a short round only inside an interactive transaction (yours, a batch's, or the one the client opens for an atomic operation). Outside one it runs one narrowed statement, and under contention its count can be lower than a plain operation's. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "writes one narrowed statement outside any transaction, without topping up a round another writer left short"
- Inside a batch `$transaction([...])`, an `updateMany` or `deleteMany` with a `limit` reads its rows after the batch's earlier operations have run, and runs narrowed to them as inside your transaction. [`many-with-limit.integration.spec.ts`](../packages/integration-tests/test/many-with-limit.integration.spec.ts): "narrows the caller's updateMany inside a batch $transaction to the rows it reads after the batch's earlier operations, and audits them"
- On PostgreSQL, a before-state read that fails in the database inside a transaction (yours, a batch's, or the one the client opens for an atomic operation) aborts that transaction, so the operation fails and rolls back. Outside a transaction the operation runs, and its record has `beforeUnavailable: true`. [`before-state-read-aborts-transaction.integration.spec.ts`](../packages/integration-tests/test/before-state-read-aborts-transaction.integration.spec.ts): "fails the caller's update and rolls it back, $scope"
- On PostgreSQL, a statement that fails inside your interactive `$transaction` (an operation of yours, audited or not, a raw query, or one of the audit's reads) aborts the transaction, and PostgreSQL answers its commit with a rollback even when the callback caught the error and resolved. So once an operation of the transaction has failed and the callback has resolved, the client runs `SELECT 1` in the transaction before committing it. On an aborted transaction, `$transaction` rejects with the error PostgreSQL answers that query with (`current transaction is aborted`), the transaction's operations are reported `not-committed`, and the audit rows written in it roll back with it. Reads after the write are separate statements too, on the same client. They read a row a nested write updated or inserted that your own `include` / `select` leaves out, a row a nested `connect`, `set` or `disconnect` re-linked, the rows an `updateMany` wrote, the rows a `createMany` created, and the fields an entity lists in `recordOmittedFields`. Outside a transaction such a read can see another writer's change made after the write. A row another writer deletes, or gives another key, before the read again of the rows an `updateMany` wrote is not recorded and is reported as `row-identification`.

#### Nested to-many creates whose keys are not known before the write

A nested to-many `create` tells the rows it created by the keys the extension generates for them, so a child another transaction commits below the same parent is not taken for one of them. The extension does not generate the key when the caller gives it, for an `autoincrement()` or other database-generated key, and for a key field the relation fills from the parent row. In those cases, and when a `createMany` with `skipDuplicates` may skip a row whose key was generated, the rows are told apart by comparing the relation after the write with the row keys read ahead of it.

A child another transaction commits below the same parent between that read and the write is then new to the relation as well. Under each parent row, the new rows are counted against the rows the writes nested under it insert: every `create` element and `createMany` row, and each `upsert` or `connectOrCreate` element whose target the read did not find. When there are more, which of them are the operation's own cannot be told. Only the rows under a key known to be the operation's are recorded then: a key the extension generated, or the whole key a `create` or `createMany` without `skipDuplicates` gives, when no write at the path writes a key field. The inserts left without a record are reported as `row-identification`, each under the nested operation that inserts it. Under `atomic` the operation fails with `AuditIncompleteError` and rolls back, and it can be retried. [`concurrent-write.postgresql.spec.ts`](../packages/integration-tests/test/concurrency/concurrent-write.postgresql.spec.ts): "records no child as created, and reports its own child as row-identification, when another transaction inserts a child under the parent between the read of its children and the write", [`concurrent-write.postgresql.spec.ts`](../packages/integration-tests/test/concurrency/concurrent-write.postgresql.spec.ts): "fails with AuditIncompleteError and rolls the write back under an atomic write when another transaction inserts a child under the parent between the read of its children and the write"

A `createMany` with `skipDuplicates` that skips a row leaves room in the count for a row another transaction inserts, which is then recorded as created, unreported.
