# @kuruwic/prisma-audit

## 0.6.1

### Patch Changes

- f5f974e: Roll back an interactive transaction whose operation failed after its write reached the database through a query extension applied after the audit, even when the callback catches the error. Before, the transaction committed such a write with no audit record when an extension applied after the audit threw after its call to `query` succeeded, called `query` a second time, or settled while its write still ran. Whether the write reached the database is now taken from the check placed innermost on the client, which sends the write, instead of from the extension's own `query` call resolving; a write the extension never sent, or sent only after the operation failed, leaves the transaction to commit. Outside any transaction such a write stays unrecorded.

## 0.6.0

### Minor Changes

- 77bca47: Reject a write that a query extension applied after the audit changes the structure of or replaces, instead of running writes the audit neither records nor rejects.
  
  - Breaking: `$extends` of an audited client (`createAuditClient(prisma).$extends(extension)`, through an extension function or `Prisma.defineExtension` alike) applies an extension with `query` as it is and places a check of the audit's own right after it, innermost on the client it derives. A model write must reach the database through every such check with arguments that, as Prisma sends them, write the same relations as the ones the audit continued it with: the same nested writes at the same places, both branches of every upsert told apart, with as many elements, in the same order within a relation field, the same `true` or `false` of a to-one `delete` or `disconnect`, and as many rows of a top-level `createMany`. Otherwise the write is rejected with `AuditExtensionContinuationError` (new, with `extensionName`, `modelName`, `operation` and `violation`) before it runs. The check reads the arguments that reach the database, so a nested write added as a class instance, behind a `toJSON`, or to the arguments once `query` was called is rejected too. Before, a nested write such an extension added ran, neither recorded nor rejected by `requireContext`. Apply an extension that changes which rows or relations an operation writes to the client passed to `createAuditClient`.
  - Breaking: the write must run through `query` once, and again only after a failed attempt. An extension that settles without the write having run, replacing the operation (a soft delete) or swallowing a failed attempt to return a result of its own, is rejected with `AuditExtensionContinuationError` once it settles; a call to `query` once the write ran, while it runs, or once it settled is rejected before it runs. In a chain of extensions the error names the extension at fault. Before, the audit recorded the operation that never ran from the extension's result.
  - Values may change: an extension that transforms the values a write writes and the rows a read returns, as field encryption does, still belongs after the audit, where the after state holds the values the application reads. The values and the fields that pick rows, those of the top-level `where` and of the unique `where` and filters of nested writes, are not compared: an extension that changes them, a tenant filter adding a field to every `where` included, must make the same change to the reads it handles.
  - A nested write the application passes behind a `toJSON` to the audited client is read as Prisma sends it, and audited.
  - `AuditUnboundWriteError` is thrown as well for a model write that reaches the check after an extension applied after the audit without the audit continuing it.
  - `AuditParentWriteError`'s message leads with writing through `Prisma.getExtensionContext(this)` or the audited client.
- 12f76b2: Run the audit of an operation outside any transaction on the client the operation was issued on, so the extensions applied after the audit see the audit's own queries there as they do inside a transaction.
  
  - Outside any transaction, the audit's reads before and after the write, its pre-reads of nested writes, the audit-log write, and the client handed to the resolvers, the enrichers and the writer (`db`, `handle`) are the audited client the operation was issued on: the client `createAuditClient` returned, or a client `$extends` derives from it. Before, they were always the client `createAuditClient` returned, so a query extension applied after the audit that transforms stored values (field encryption) left the stored values in the before state of a record whose after state held the values the application reads. Inside a transaction they already ran on the transaction's client, which carries those extensions. For an operation issued on the client `createAuditClient` returned nothing changes.

## 0.4.0

### Minor Changes

- 03ff457: Roll back a transaction PostgreSQL aborted on a caught failure, never audit the writer's own writes, and bind `$parent` like the client it is read from.
  
  - Breaking: on PostgreSQL, a `$transaction` callback that catches a failed statement (an operation of yours, audited or not, a raw query, or one of the audit's reads) without rolling back to a savepoint, and then resolves, rejects with the error PostgreSQL returns for an aborted transaction (`current transaction is aborted, commands ignored until end of transaction block`). The transaction rolls back, its operations are reported `not-committed`, and its audit logs roll back with it. Once an operation of a transaction has failed, the client runs `SELECT 1` in it before committing; a transaction without a failure runs no extra query, and one still usable after the failure commits as usual.
  - A write `write.writer` makes through the audited client is not audited under any write mode, like a write any other user callback makes.
  - `Prisma.getExtensionContext(this).$parent`, read in a client or model method an extension applied to the audited client adds, is wrapped like the client the method was called on: the audited client outside any transaction, and bound to the transaction on a `$transaction` callback's client. A write through it is audited, in that transaction.
- 03ff457: Replace `errorObserver` with `observer`, called once per audited write with the outcome of its audit.
  
  - Breaking: `errorObserver`, `AuditErrorObserver`, `AuditErrorContext` and `AuditErrorPhase` are removed. `observer?: AuditObserver` is called once for every operation that writes rows of a model in `entities`, nested writes included, with an `AuditOutcome`: `{ model, operation, status, unauditedReason?, records, failures, unrecordedWrites }`.
    - `status`: `complete` (committed, and every audit log was passed to a writer that resolved; a committed atomic operation is always `complete`), `incomplete` (committed without some of its audit logs, under `awaited` or `deferred`), `not-committed` (the operation failed, or its transaction rolled back or failed to commit), or `unaudited` with `unauditedReason: 'no-context'`. `records` counts the audit logs passed to a writer that resolved.
    - `failures` are `AuditFailure`s typed by `phase`: `pre-fetch` (`modelName`, `operation`, `error`), `row-identification` (`modelName`, `operation`, `unidentified`, `error`), `id-resolver-call` (`modelName`, `operation`, `identity`, `resolver`, `error`), `diff-generation` (`error`) and `log-write` (`records`, `error`). They carry no `params`. `unrecordedWrites` lists the writes left without an audit log as `{ modelName, operation, path }`.
    - Outside any transaction the outcome is reported before the operation returns or throws, or, under `deferred`, once the detached audit write has run. Inside a transaction the outcomes are reported once it commits, or as `not-committed` once it rolls back, so an operation in a transaction that rolls back is never reported `complete`.
    - Without an observer, the failures of an `incomplete` outcome are logged to the console. A write the observer makes through the audited client is not audited.
  - Core API: `createFailureSink`, `FailureSink`, `FailureSinkConfig` and `WritePlan` are removed. `createOperationOutcome(target, { observer })` returns the `OperationOutcome` an adapter reports a write's failures and unrecorded writes to and settles once the write's fate is known; `droppedRecords()` tells whether an atomic write must fail. `dispatch` takes the write's `outcome` in place of `modelName`, `operation` and `params`, and `DispatchConfig` has no `failureSink`. `auditGate` returns `unaudited` (`reason: 'no-context'`) for a write of audited models without an audit context, and `skip` only for a write of no audited model.
- 03ff457: Write the audit rows of every operation inside a transaction in that transaction, whatever its write mode, so that they commit and roll back with the rows they record.
  
  - Breaking (behaviour): under `deferred`, an operation inside a transaction writes its audit rows in the transaction before it returns, as under `awaited`, where `write.awaited: false` queued them until the commit. A rollback the adapter cannot see (a raw `ROLLBACK TO SAVEPOINT`, PostgreSQL aborting the transaction, a nested transaction that rolls back) leaves no audit rows for rows that do not exist. A failed audit write inside a transaction fails the operation and keeps the transaction from committing under every mode; the writer receives the transaction's client and `inTransaction: true`. Outside any transaction `deferred` still writes detached.
  - Core: the `after-commit` write plan is gone. Inside a transaction `dispatch` writes the records on the transaction's handle under every mode, and nothing runs after a transaction's commit.
  - `@kuruwic/prisma-audit`: audited operations and nested transactions of one transaction are ordered so that no operation's statements straddle a savepoint. A nested `tx.$transaction(...)` opens once the enclosing transaction's running audited operations have settled, except the one it is opened from; an audited operation started on `tx` while it opens runs inside it, and one started while it is being released or rolled back runs after it, in the enclosing transaction. Once a `$transaction` callback has resolved or thrown, the transaction waits for the audited operations it started without awaiting before it commits or rolls back; the wait counts against its `timeout`.
  - Do not issue transaction-control SQL through raw queries (`SAVEPOINT`, `RELEASE`, `ROLLBACK TO`, `COMMIT`, `ROLLBACK`) while an audited operation of the same transaction is running; awaiting the operation is enough. The outcome of a write undone by a raw `ROLLBACK TO SAVEPOINT` stays `complete`.
- 03ff457: Bind every audited operation to the client it was issued on, run a batch `$transaction([...])` holding a model write as one interactive transaction, and roll back a transaction whose callback swallowed an audit failure.
  
  - Fix: a write on the audited client inside an interactive `$transaction` callback (`prisma.user.create(...)` inside `prisma.$transaction(async (tx) => ...)`) commits on its own, but its audit row was written in the callback's transaction, so a callback that threw left the write without its audit row. The audit takes an operation's transaction from the client it was issued on: such a write is audited as a write outside any transaction, and a write on `tx` in the callback's transaction.
  - Behavior change: every call on a model delegate or raw-query method of the audited client, of a client derived from it, and of the client a `$transaction` callback receives returns the library's lazy operation. It is not a PrismaPromise: a batch accepts only operations of its own client that have not run, and Prisma's own `$transaction` of another client rejects them.
  - Behavior change: a batch `$transaction([...])` holding a model write (`create`, `createMany`, `createManyAndReturn`, `update`, `updateMany`, `updateManyAndReturn`, `upsert`, `delete`, `deleteMany`), audited or not, runs as one interactive transaction at the batch's `isolationLevel`, its operations one after another. Each operation's audit reads see what earlier operations of the batch wrote, so an `updateMany` or `deleteMany` with a `limit` is recorded instead of being reported as `row-identification`, and a `createMany` row a later operation deletes is recorded as created. A failure of any operation's audit rolls back the whole batch. The batch holds a connection and is bound by the client's `transactionOptions`. A batch of reads and raw queries only, `$executeRaw` included, stays Prisma's own batch.
  - `AuditRollbackError`: when an audit failure fails an operation inside an interactive transaction after its write ran (a failed audit write, a failed build of the records) and the callback catches the error and resolves, `$transaction` rejects with it (`cause`: the audit error) and the transaction rolls back.
  - `AuditUnboundWriteError` (exported): an audited write that reaches the audit without the binding of the client it was issued on, such as one inside a batch Prisma runs itself, is rejected before it runs.
- 03ff457: Record no create for a child another writer inserts below a parent row while a nested to-many create whose keys the extension does not generate runs.
  
  - The rows new below a parent row are counted against the rows the operation's nested creates insert under it. When more rows are new, only the rows whose key shows they are the operation's (a key the extension generated, or a whole key a `create`, or a `createMany` without `skipDuplicates`, gives) are recorded. The other inserts are reported as `row-identification` under the nested write that inserts them; under `atomic` the operation fails with `AuditIncompleteError` and rolls back.
  - When several elements of an operation name the same parent row, the creates nested under each of them are counted, and an inserted row whose key shows which create inserted it is recorded for that create.
- 03ff457: Audit transactions nested in an interactive transaction, hand an extension function the audited client, load with `require`, and type the audited client as the client it extends.
  
  - A `$transaction` opened on a `$transaction` callback's client (Prisma 7.5 and later), which the database runs as a savepoint, hands its callback a client bound to it; a batch `tx.$transaction([...])` runs as one such nested transaction. Only one can be open at a time on a transaction client, as Prisma requires. A write made while one is open, through its client or the enclosing one, commits with the enclosing transaction, or, when the nested transaction rolls back to its savepoint, is reported `not-committed` and its audit rows roll back with it.
  - `$extends` called with an extension function, as `Prisma.defineExtension((client) => ...)` makes, calls the function with the audited client, so an operation the extension issues on that `client` is audited.
  - Both packages load with `require` as well as `import` on the Node.js versions their `engines` name.
  - Breaking (types): `createAuditClient` returns the type of the client it extends. The `$audit` property its type named, which the client never had, is gone.
- 03ff457: Keep a transaction from committing once an audit failure failed one of its operations, in every adapter.
  
  - Core API: `createTransactionAudit()` returns the `TransactionAudit` of one transaction an adapter owns. `outcomes` settles the outcomes of its writes; `poison(error)` records an audit failure that failed a write after the write ran; `assertCommittable()`, called between the transaction's body and its commit, throws `AuditRollbackError` (`cause`: the first failure) once one is recorded. `end(committed)` ends the audit of an outermost transaction and settles its outcomes; `mergeInto(parent, committed)` hands a nested transaction's outcomes to its parent. A nested transaction's audit failures stay its own. `settledIn(audit, outcome, run)` runs a write and settles its outcome: on the audit inside a transaction, before returning outside any. `assertRecordsComplete({ modelName, operation, mode }, outcome, audit)` throws `AuditIncompleteError` for an atomic write that lost records and records it on the audit.
  - Breaking (core): `TransactionRuntime.transaction` is `{ handle, audit }` in place of `{ handle, afterCommit }`. `dispatch` records the error it rejects with on the transaction's audit.
  - `AuditRollbackError` is exported by both packages.
- 03ff457: Replace `write.awaited` and `write.implicitTransaction` with `write.mode`, make every audited write atomic by default, and remove sampling.
  
  - Breaking: `samplingRate` is removed from the core and the Prisma extension. Every change to an audited model is recorded, except writes of models not in `entities` and writes without an audit context that `requireContext` does not reject.
  - Breaking: `write.mode?: WriteMode` (`'atomic' | 'awaited' | 'deferred'`, default `'atomic'`) replaces `write.awaited` and `write.implicitTransaction`, and `defineEntity({ ..., writeMode })` gives a model its own mode. An operation takes the strongest mode (`atomic`, then `awaited`, then `deferred`) of the audited models it writes rows of, nested writes included.
    - `atomic`: the operation commits only together with every audit row it should produce. Inside your `$transaction` the rows are written in it; outside any transaction the audited client opens an interactive transaction around the operation at the client's default isolation level, as `write.implicitTransaction: true` did. That transaction costs its round trips, a connection held until it commits, and the client's `transactionOptions` limits. A driver adapter without interactive transactions, such as Cloudflare D1's, needs `awaited` or `deferred`.
    - `awaited`: what `write.awaited: true` without `write.implicitTransaction` did: the rows are written once the operation has committed, before it returns.
    - `deferred`: what `write.awaited: false` did outside a transaction: the rows are written detached.
  - `AuditIncompleteError` (new, with `modelName`, `operation`, `failures`, also its `cause`, and `unrecordedWrites`): under `atomic`, a failure that drops an audit row fails the operation with it and rolls its transaction back. Such failures are `row-identification`, `id-resolver-call`, and a `pre-fetch` failure that leaves an `upsert` or `connectOrCreate` entry, or a row a nested link write unlinks without naming it, unrecorded. A row recorded with `beforeUnavailable: true` is not dropped. Under `awaited` and `deferred` these failures are reported only. Under concurrent writes, an `updateMany` or `deleteMany` whose `where` another writer changed, or a `createMany` with `skipDuplicates` whose count check does not match, fails under `atomic` and can be retried.
  - `AuditAtomicityError` (new, with `modelName` and `operation`): an atomic operation that reaches the audit outside any transaction the client owns is rejected before it runs. This happens when an extension applied before the audit adds a nested write of an atomic model to a call that is not atomic itself.
  - Core API: `policy(auditedModels, { mode, entity })` takes the audited models the write writes rows of in place of one model name and returns the write's `WriteMode`, and `planFor(mode, inOwnedTransaction)` its `WritePlanKind` (`immediate`, `awaited-after-commit` or `detached`) or `'reject'`. `dispatch` takes `plan` in place of `atomic`. `WriteMode`, `WritePlanKind`, `planFor`, `AuditAtomicityError` and `AuditIncompleteError` are exported; `WritePolicy` is removed.

## 0.3.0

### Minor Changes

- 86ba977: Decide whether a write is audited from the audited models it writes, and add `requireContext`.
  
  - `@kuruwic/db-audit-core` adds `auditGate`, which returns `audit` (with the audit context), `skip` or `reject` from the audit context set for a write, if any, and the audited models it writes rows of, and `AuditContextMissingError`, which an adapter throws for a rejected write. `policy()` and `WritePolicy` are unchanged; the gate runs before the write policy, and sampling does not affect it.
  - `@kuruwic/prisma-audit` adds the `requireContext` option (`boolean | ((modelName) => boolean)`, default `false`). Without an audit context, an operation that writes rows of a model in `entities` that `requireContext` holds for, nested writes included, is rejected with `AuditContextMissingError` before Prisma runs it, at any `samplingRate`. A nested `connect`, `set` or `disconnect` counts the related model only when the related rows hold the foreign key. `AuditContextMissingError` is exported from the package entry.
  - Behavior change in `@kuruwic/prisma-audit`: an operation on a model that is not in `entities` is audited when its nested writes write rows of a model that is, and those rows are now recorded. Before, the whole operation was skipped. `samplingRate` and `write.awaited` are still called with the operation's own model, which may now be one that is not in `entities`.
  - Behavior change in `@kuruwic/audit-adapter-memory`, the private reference adapter of the core: a write without an audit context now runs unaudited instead of throwing (set `requireContext` to reject it), and a write of a model that is not in `entities` no longer consults the write policy or the actor enricher.
- eb40d58: Report an `updateMany` or `deleteMany` whose count shows that another writer changed its rows between the audit's read and the write.
  
  The rows these operations audit are the rows a `findMany` reads ahead of the write. Each mismatch is reported to `errorObserver` as `row-identification` with `params: { unidentified }`, and the records are unchanged:
  
  - an `updateMany` whose count is above the rows it read: a row another writer made match the `where` was updated without a record
  - an `updateMany` whose count is below the read rows it finds again after the write: a row another writer moved out of the `where` was not updated, and the audit cannot tell which, so it treats every row it finds as updated
  - a `deleteMany` whose count is below the rows it read: a row another writer deleted first is still recorded as deleted
  - a `deleteMany` whose count is above the rows it read: a row another writer made match the `where` was deleted without a record
  
  A swap that leaves the count unchanged is not seen. An `updateMany` or `updateManyAndReturn` whose `data` gives no field a value (every field `undefined` or `Prisma.skip`) changes no row: it runs as given, with no row read or recorded, and no count compared, since Prisma runs no `UPDATE` for it and the count it returns is not the rows written (0 on SQLite).
- 7c64961: Fail the caller's operation when its audit write inside a transaction fails, and remove `write.onError`.
  
  - Fix: inside a transaction (an interactive `$transaction`, or the one `write.implicitTransaction` opens), an awaited audit-log write that failed under the default `write.onError: 'log'` was swallowed, so the operation and `$transaction` resolved with the written row. When the insert failed in the database, PostgreSQL had aborted the transaction and COMMIT rolled it back: neither the data change nor an audit row existed. InnoDB rolls a whole transaction back on a deadlock, so MySQL could lose data the same way. The library cannot tell whether a transaction survived a failed statement, so an awaited write inside a transaction that has not committed (the `immediate` write plan) now always fails the caller's operation with the write's original error, after notifying `errorObserver` under `log-write`. Use `write.awaited: false` for a model whose writes should succeed when their audit write fails.
  - A failed write after the operation has committed (awaited outside any transaction, queued until commit, or detached) and the dropped records of a committed write whose build failed never fail the operation, as before.
  - Breaking: `write.onError` is removed from `@kuruwic/prisma-audit`, and `FailureSinkConfig.writeOnError` and the `WriteOnError` type are removed from `@kuruwic/db-audit-core` and from the `@kuruwic/prisma-audit` exports. No outcome is left for them to decide.
  - Console output: without an `errorObserver`, a failure the caller cannot see (a failed write of a committed operation, or a dropped build) is logged to the console, as under the former default. With an observer, only the observer receives it. A failed write that fails the operation writes no console line. An observer that throws is logged together with the message of the failure it was given.
  - `@kuruwic/audit-adapter-memory`, the private reference adapter of the core, drops its `write.onError` option (whose default was `'throw'`). Because it always observes failures to fill `writeFailures` and `resolverFailures`, the core failure sink no longer logs its post-commit failures or dropped builds to the console.
- 5e8c5a1: Tell the rows a nested to-many create inserts by the keys the extension generates for them, instead of by the rows that appeared.
  
  Below a row that exists before the operation, a nested `create`, `createMany`, or the `create` of an `upsert` or `connectOrCreate` whose target does not exist, inserts rows next to the rows the relation already holds. They were told apart by the primary keys the relation held before the write, read ahead of it, so a child another transaction inserted below the same parent in between was recorded as created by the nested create.
  
  - Behavior change: when such a row's data leaves out every row-key field and each has a `cuid()`, `cuid(2)`, `uuid()`, `uuid(4)` or `uuid(7)` default, the extension now fills them in before the write with the same generator, as it does for a top-level `createMany`. Query extensions applied after the audit extension, and the value Prisma returns, see that key.
  - The created rows are the rows with the keys the extension generated; a child another writer inserts is not recorded, and no row of the relation is read before the write.
  - A row whose key the extension does not generate (one the caller gives, which the database may store in another form or a later write of the operation may change; an `autoincrement()` key; a key field the relation fills from the parent row), the rows of a relation another write of the operation gives a key field to, and the rows of a `createMany` with `skipDuplicates`, are still told apart by the row keys read ahead of the write, with the race above.
- 6e14827: Record nested writes to a model identified by a unique constraint instead of a primary key.
  
  A nested write into a model with no `@id` or `@@id`, identified by `@unique` or `@@unique` on required fields, was neither recorded nor reported: the nested pipeline told rows apart by their primary key only. It now tells them apart by the model's row key, the one batch operations already use: the primary key, else the first unique constraint whose fields are all required.
  
  - A nested `create`, `createMany`, `update`, `upsert`, `delete`, `updateMany`, `deleteMany`, `connect`, `disconnect`, `set` or `connectOrCreate` into such a model, and the writes nested below one of its rows, record one log per row they write.
  - The message of the error a nested delete whose key cannot be resolved reports now says "row key" instead of "primary key". Behavior change: its `params.pkFields` is renamed `params.keyFields`, the fields of the row key.
- 3ec52b3: Record a nested update that gives its row another key under the key the write gives it.
  
  A nested `update`, the update branch of a nested `upsert` or a nested `updateMany` whose data wrote the row key of the rows it updated (the primary key, or the unique constraint of a model without one) found the rows again after the write by the key they had before it, so they were not found and not recorded, and nothing was reported.
  
  - The rows are now found by the key the write gives them: the key they had with the key fields the data gives literal values (a value, or `{ set: value }`) replaced, as top-level batch updates already do. With `fetchBefore.update: false`, an update whose `where` names the whole row key is found the same way.
  - Behavior change: a write whose data changes the key in a way its arguments do not tell (an operator such as `increment` on a key field, a relation whose foreign key is part of the key, or a nested `updateMany` with several elements of which one writes the key) is reported to the observer as `row-identification`, with `params: { path, unidentified }`. Its rows are still not recorded.
  - A row key that holds the foreign key to the parent row (`@@unique([deviceCode, slot])` with `deviceCode` referencing the parent) is compared with those fields taken from the parent row as it is after the write. A row a nested `connect` moves in from another parent is recorded once, as the change of its foreign key, under its new key, instead of as a create (or not at all). A row a nested `updateMany` writes below a parent whose referenced column the same operation changes is recorded under the key `ON UPDATE CASCADE` gives it, the foreign-key change in its `changes`, and a row that change re-keys is no longer recorded as created next to a nested `create`. A nested `update` or `upsert` below such a parent names its row by the parent's new value, since Prisma writes the parent first; its read ahead of the write now names the row by the parent's value before the write, so an update is recorded with its before state and changes (it was recorded with none, and an upsert taking its update branch as a create), and a value the parent's data does not tell leaves the before state unavailable.
  - Behavior change: targets at one path that their keys after the write cannot tell apart (targets naming different rows that end up with the same key, and a target naming the key another target's write gives a row) are reported as `row-identification` instead of being recorded with another row's before state.
  - Behavior change: at a path holding a row whose key after the write is unknown, the rows a nested write inserts without a key the extension generated are no longer recorded as created; they are reported as `row-identification` once per inserting operation, with `params: { path, unidentified }` and a message saying they cannot be told apart from a row whose key the write changed. Rows with a key the extension generated are still recorded.
