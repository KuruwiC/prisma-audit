# @kuruwic/db-audit-core

## 0.6.0

No changes in this release.

## 0.5.0

### Minor Changes

- 994ff5f: Redact the enriched contexts and the request context as the states are, so a secret in a context is no longer stored in clear.
  
  - Breaking: `actorContext`, `entityContext`, `aggregateContext` and `requestContext` mask the built-in sensitive fields (`password`, `token`, `apiKey` and the like) and `redactFields` at any depth, after the serializers ran, as `before`, `after` and `changes` do. Before, they were stored as the enrichers and the context provider returned them. A field that a context needs in clear must not share a name with a sensitive field or one in `redactFields`.
  - Only the keys of the structure the serializers output are masked: a serializer that turns an object into a string hides the keys inside it, which are stored in clear.
- a2e55c7: Report an enricher that falls back in the write's outcome, so a record stored without its context is no longer reported as if nothing failed.
  
  - Breaking: an enricher whose `onError` is, or resolves to, `'log'` or `'ignore'` and that fails (an error, a timeout, or a batch result of the wrong length) is listed in the outcome's `failures` as `{ phase: 'enrichment', enricher: 'actor' | 'entity' | 'aggregate', error }`, once per enricher call. The record is stored with the `fallback` as before, the outcome stays `complete`, and an `atomic` write does not fail. `'ignore'` only keeps the failure off the console. An observer that treats every listed failure as a lost record must look at `status` or the phase instead, and a `switch` over `AuditFailure['phase']` has a new case.
  - Breaking (core API): the `ResolveFailure` that `resolve` reports to its `ResolveFailureSink` (`OperationOutcome.reportResolveFailure`) is a union keyed by `phase`: `id-resolver-call` or `enrichment`. `FailedEnricher` names the kind of enricher.
  - Without an observer, the `enrichment` failures of an `incomplete` outcome are not logged to the console, as they lost no record.
- 1c87805: Report in each write's outcome the transaction its audit reads and its write ran in, so a `complete` outcome is no longer read as a guarantee that its records are accurate under concurrent writes.
  
  - Breaking: every `AuditOutcome` carries `isolation` (`AuditIsolation`): `{ kind: 'no-transaction' }` when the reads and the write share no transaction (outside any transaction: an `awaited` or `deferred` write, or one without an audit context), `{ kind: 'undeclared' }` in a transaction opened without an isolation level the audit sees, or `{ kind: 'declared', level }` in one opened at a declared level. `complete` still means every record was passed to a writer that resolved; it does not cover accuracy, whose premise is `isolation`.
  - Breaking (core API): `OutcomeTarget`, what `createOperationOutcome` takes, requires `isolation`. The core treats the level as an opaque name.
  - `@kuruwic/prisma-audit`: the declared level is the `isolationLevel` option of the outermost `$transaction` the operation runs in, interactive or batch; a nested `$transaction` does not change it. A level the client's `transactionOptions` set is not seen, and is reported `undeclared`.
  - `@kuruwic/prisma-audit`: new `write.isolationLevel` opens the transaction the client opens for an `atomic` write outside any transaction at that level, and reports it `declared`; `createAuditClient` throws for a value that is not one of the generated client's `Prisma.TransactionIsolationLevel`. Unset, the transaction runs at the client's default, as before. The library does not retry a transaction that fails with `P2034`.
- 4728e79: Reject every write through a `$parent` below the audit, instead of running it unaudited.
  
  - Breaking: `$parent`, of a client or of a model delegate, and `Prisma.getExtensionContext(this).$parent` keep Prisma's meaning, the client one level below without the extensions applied above it. Below the level the audit was applied to (the audited client's `$parent`, the client passed to `createAuditClient` and the clients under it, inside a transaction their transaction clients) it runs the extensions applied before the audit, which may change a write's arguments where the audit cannot see, so every write through it, of a model in `entities` or not, is rejected with `AuditParentWriteError` (new, with `modelName`, `operationModelName` and `operation`) before Prisma runs any of it. The client decides it when the write starts, from the client's level and the action alone, never from the arguments. So is a write in a batch or interactive `$transaction` opened on such a client, in a transaction nested on it, or through a client `$extends` derives from it. Before, it ran unaudited. Such a client still reads and runs raw queries, and a rejected write has no outcome.
  - Breaking: in a method of an extension applied before the audit (to the client passed to `createAuditClient`), called on the audited client, a write through `Prisma.getExtensionContext(this).$parent` is rejected that way. Apply an extension that writes to the audited client (`createAuditClient(prisma).$extends(extension)`), or write through `Prisma.getExtensionContext(this)` or the audited client.
  - Breaking: such a write issued from a callback the audit runs, through the `$parent` of the client it receives (`db`, the writer's `handle`), is rejected with `AuditParentWriteError` too. Inside a transaction those callbacks receive the client bound to it, the one an interactive `$transaction` callback receives, instead of Prisma's transaction client.
  - Breaking (`@kuruwic/db-audit-core`): `RejectedWriteError`, the base of `AuditContextMissingError` and `AuditReentrantWriteError`, is exported, and `AuditParentWriteError` extends it. An enricher's `onError` cannot turn any `RejectedWriteError` into a fallback, and the rejection of such a write an enricher issues once it has timed out is logged to the console.
  - A model delegate read by its schema name (`client.User`), which Prisma exposes next to `client.user`, is wrapped the same way on every client: through the audited client a write is audited, and below the audit it is rejected. Before, it reached Prisma's own delegate.
  - Outside any transaction `$parent` is one client per client below, wherever it is read: the `$parent` of a client `$extends` derives from the audited client is the audited client, so a batch `$transaction([...])` on it takes the audited client's operations.
  - The `$parent` of a client an extension applied after the audit adds (`createAuditClient(...).$extends(...)`) is still the client below it, with the methods of the extensions between, and a write through it is audited.
  - Overriding a built-in action (`create`, `update`, ...) with a model extension applied before the audit is unsupported: Prisma calls such a method with its own delegate as `this`, so a write it makes through `Prisma.getExtensionContext(this).$parent` runs unaudited and is not rejected. Change a built-in operation with a query extension instead.
  - To bypass the audit on purpose, write through a client your application holds itself, the client passed to `createAuditClient` or another `PrismaClient`, or through raw SQL. A write of a model in `entities` without an audit context also runs unaudited when `requireContext` does not hold for it.
- 5f95fe8: Reject a write of an audited model issued while the audit processes an operation, such as one a user callback makes, instead of running it unaudited.
  
  - Breaking: a write of a model in `entities`, nested writes included, that a resolver, an enricher or its `onError`, the writer or the observer issues while the audit processes an operation is rejected with `AuditReentrantWriteError` (new, with `modelName`, `operationModelName` and `operation`, exported by both packages) before Prisma runs any of it, with or without an audit context, and has no outcome. Before, it ran unaudited, and outside any transaction a write through the client a callback received was not even seen by the audit. The callback then fails as on any error of its own: a resolver is reported as `id-resolver-call`, an enricher or its `onError` as `diff-generation`, the writer as `log-write`, and the observer's error is logged and ignored. A write of a model that is not in `entities` still runs. A write meant to run unaudited goes through the client passed to `createAuditClient`.
  - Breaking: outside any transaction, the `db` a resolver or an enricher receives, and the writer's `handle`, are the audited client instead of the client passed to `createAuditClient`; inside a transaction they are still a client of that transaction. The default write and the audit's own reads run on the same client.
  - A write of an extension applied after the audit that it issues while handling one of the audit's own queries is rejected the same way.
  - An enricher's `onError`, whatever it says, rethrows `AuditReentrantWriteError`, from the enricher or from the `onError` function itself. An enricher that has timed out has been handled by `onError` already: a write it issues afterwards is rejected the same way, and the rejection is logged with `console.error`.
  - Core API: `auditGate({ context, auditedModels, withinAudit }, config)` takes the write as one input (`AuditGateInput`), and returns `reentrant` (with `modelName`) for a write of audited models issued while the audit processes an operation, before it looks at the audit context. An adapter throws `AuditReentrantWriteError` for it and creates no outcome.
  - Core API: `logIncompleteOutcome`, the reporting of an outcome when no observer is given (the failures of an `incomplete` outcome logged to the console), is exported, for an adapter that observes the outcomes itself to call when the user gives no observer.
- 7c65bd0: Reject a write of an audited model without an audit context by default, instead of running it unaudited.
  
  - Breaking: `requireContext` defaults to `true`. A write without an audit context that writes rows of a model in `entities`, nested writes included, is rejected with `AuditContextMissingError` before Prisma runs any of it. Before, it ran unaudited, and with no `observer` nothing recorded that it did. Run a seed, a migration script or a batch job under an audit context with a system actor (`provider.runAsync({ actor: { category: 'system', type: 'Seeder', id: 'seed' } }, ...)`), or set `requireContext` to `false`, or to a function that returns false for the models whose writes may run unaudited.
  - `AuditContextMissingError`'s message says how to resolve it: set an audit context with the context provider's `runAsync`, or opt the model out with `requireContext`.
  - Breaking (core API): `AuditGateConfig.requireContext` is optional, and `auditGate` reads it unset as `true`. An adapter passes the user's value through and does not default it.
- e6601d8: Report a resolver failure when it happens, so an enricher that throws later no longer erases it.
  
  - Fix: the `id-resolver-call` failures of an operation stay in its outcome when an enricher then throws (reported as `diff-generation`); before, they were lost with the resolution.
  - Breaking (core API): `resolve(events, auditContext, config, read, sink)` reports each resolver failure to `sink` (`ResolveFailureSink`, taking an `id-resolver-call` `ResolveFailure`) as it fails, and returns the resolved events alone; `Resolution` and `ResolverFailure` are removed. `OperationOutcome.reportResolveFailure` is that sink, in place of `reportResolverFailures`.

## 0.4.0

### Minor Changes

- 03ff457: Replace `errorObserver` with `observer`, called once per audited write with the outcome of its audit.
  
  - Breaking: `errorObserver`, `AuditErrorObserver`, `AuditErrorContext` and `AuditErrorPhase` are removed. `observer?: AuditObserver` is called once for every operation that writes rows of a model in `entities`, nested writes included, with an `AuditOutcome`: `{ model, operation, status, unauditedReason?, records, failures, unrecordedWrites }`.
    - `status`: `complete` (committed, and every audit log was passed to a writer that resolved; a committed atomic operation is always `complete`), `incomplete` (committed without some of its audit logs, under `awaited` or `deferred`), `not-committed` (the operation failed, or its transaction rolled back or failed to commit), or `unaudited` with `unauditedReason: 'no-context'`. `records` counts the audit logs passed to a writer that resolved.
    - `failures` are `AuditFailure`s typed by `phase`: `pre-fetch` (`modelName`, `operation`, `error`), `row-identification` (`modelName`, `operation`, `unidentified`, `error`), `id-resolver-call` (`modelName`, `operation`, `identity`, `resolver`, `error`), `diff-generation` (`error`) and `log-write` (`records`, `error`). They carry no `params`. `unrecordedWrites` lists the writes left without an audit log as `{ modelName, operation, path }`.
    - Outside any transaction the outcome is reported before the operation returns or throws, or, under `deferred`, once the detached audit write has run. Inside a transaction the outcomes are reported once it commits, or as `not-committed` once it rolls back, so an operation in a transaction that rolls back is never reported `complete`.
    - Without an observer, the failures of an `incomplete` outcome are logged to the console. A write the observer makes through the audited client is not audited.
  - Core API: `createFailureSink`, `FailureSink`, `FailureSinkConfig` and `WritePlan` are removed. `createOperationOutcome(target, { observer })` returns the `OperationOutcome` an adapter reports a write's failures and unrecorded writes to and settles once the write's fate is known; `droppedRecords()` tells whether an atomic write must fail. `dispatch` takes the write's `outcome` in place of `modelName`, `operation` and `params`, and `DispatchConfig` has no `failureSink`. `auditGate` returns `unaudited` (`reason: 'no-context'`) for a write of audited models without an audit context, and `skip` only for a write of no audited model.
- 03ff457: Write the audit rows of every operation inside a transaction in that transaction, whatever its write mode, so that they commit and roll back with the rows they record.
  
  - Breaking (behaviour): under `deferred`, an operation inside a transaction writes its audit rows in the transaction before it returns, as under `awaited`, where `write.awaited: false` queued them until the commit. A rollback the adapter cannot see (a raw `ROLLBACK TO SAVEPOINT`, PostgreSQL aborting the transaction, a nested transaction that rolls back) leaves no audit rows for rows that do not exist. A failed audit write inside a transaction fails the operation and keeps the transaction from committing under every mode; the writer receives the transaction's client and `inTransaction: true`. Outside any transaction `deferred` still writes detached.
  - Core: the `after-commit` write plan is gone. Inside a transaction `dispatch` writes the records on the transaction's handle under every mode, and nothing runs after a transaction's commit.
  - `@kuruwic/prisma-audit`: audited operations and nested transactions of one transaction are ordered so that no operation's statements straddle a savepoint. A nested `tx.$transaction(...)` opens once the enclosing transaction's running audited operations have settled, except the one it is opened from; an audited operation started on `tx` while it opens runs inside it, and one started while it is being released or rolled back runs after it, in the enclosing transaction. Once a `$transaction` callback has resolved or thrown, the transaction waits for the audited operations it started without awaiting before it commits or rolls back; the wait counts against its `timeout`.
  - Do not issue transaction-control SQL through raw queries (`SAVEPOINT`, `RELEASE`, `ROLLBACK TO`, `COMMIT`, `ROLLBACK`) while an audited operation of the same transaction is running; awaiting the operation is enough. The outcome of a write undone by a raw `ROLLBACK TO SAVEPOINT` stays `complete`.
- 03ff457: Keep a transaction from committing once an audit failure failed one of its operations, in every adapter.
  
  - Core API: `createTransactionAudit()` returns the `TransactionAudit` of one transaction an adapter owns. `outcomes` settles the outcomes of its writes; `poison(error)` records an audit failure that failed a write after the write ran; `assertCommittable()`, called between the transaction's body and its commit, throws `AuditRollbackError` (`cause`: the first failure) once one is recorded. `end(committed)` ends the audit of an outermost transaction and settles its outcomes; `mergeInto(parent, committed)` hands a nested transaction's outcomes to its parent. A nested transaction's audit failures stay its own. `settledIn(audit, outcome, run)` runs a write and settles its outcome: on the audit inside a transaction, before returning outside any. `assertRecordsComplete({ modelName, operation, mode }, outcome, audit)` throws `AuditIncompleteError` for an atomic write that lost records and records it on the audit.
  - Breaking (core): `TransactionRuntime.transaction` is `{ handle, audit }` in place of `{ handle, afterCommit }`. `dispatch` records the error it rejects with on the transaction's audit.
  - `AuditRollbackError` is exported by both packages.
- 03ff457: Replace `write.awaited` and `write.implicitTransaction` with `write.mode`, make every audited write atomic by default, and remove sampling.
  
  - Breaking: `samplingRate` is removed from the core and the Prisma extension. Every change to an audited model is recorded, except writes of models not in `entities` and writes without an audit context that `requireContext` does not reject.
  - Breaking: `write.mode?: WriteMode` (`'atomic' | 'awaited' | 'deferred'`, default `'atomic'`) replaces `write.awaited` and `write.implicitTransaction`, and `defineEntity({ ..., writeMode })` gives a model its own mode. An operation takes the strongest mode (`atomic`, then `awaited`, then `deferred`) of the audited models it writes rows of, nested writes included.
    - `atomic`: the operation commits only together with every audit row it should produce. Inside your `$transaction` the rows are written in it; outside any transaction the audited client opens an interactive transaction around the operation at the client's default isolation level, as `write.implicitTransaction: true` did. That transaction costs its round trips, a connection held until it commits, and the client's `transactionOptions` limits. A driver adapter without interactive transactions, such as Cloudflare D1's, needs `awaited` or `deferred`.
    - `awaited`: what `write.awaited: true` without `write.implicitTransaction` did: the rows are written once the operation has committed, before it returns.
    - `deferred`: what `write.awaited: false` did outside a transaction: the rows are written detached.
  - `AuditIncompleteError` (new, with `modelName`, `operation`, `failures`, also its `cause`, and `unrecordedWrites`): under `atomic`, a failure that drops an audit row fails the operation with it and rolls its transaction back. Such failures are `row-identification`, `id-resolver-call`, and a `pre-fetch` failure that leaves an `upsert` or `connectOrCreate` entry, or a row a nested link write unlinks without naming it, unrecorded. A row recorded with `beforeUnavailable: true` is not dropped. Under `awaited` and `deferred` these failures are reported only. Under concurrent writes, an `updateMany` or `deleteMany` whose `where` another writer changed, or a `createMany` with `skipDuplicates` whose count check does not match, fails under `atomic` and can be retried.
  - `AuditAtomicityError` (new, with `modelName` and `operation`): an atomic operation that reaches the audit outside any transaction the client owns is rejected before it runs. This happens when an extension applied before the audit adds a nested write of an atomic model to a call that is not atomic itself.
  - Core API: `policy(auditedModels, { mode, entity })` takes the audited models the write writes rows of in place of one model name and returns the write's `WriteMode`, and `planFor(mode, inOwnedTransaction)` its `WritePlanKind` (`immediate`, `awaited-after-commit` or `detached`) or `'reject'`. `dispatch` takes `plan` in place of `atomic`. `WriteMode`, `WritePlanKind`, `planFor`, `AuditAtomicityError` and `AuditIncompleteError` are exported; `WritePolicy` is removed.

### Patch Changes

- 03ff457: Audit transactions nested in an interactive transaction, hand an extension function the audited client, load with `require`, and type the audited client as the client it extends.
  
  - A `$transaction` opened on a `$transaction` callback's client (Prisma 7.5 and later), which the database runs as a savepoint, hands its callback a client bound to it; a batch `tx.$transaction([...])` runs as one such nested transaction. Only one can be open at a time on a transaction client, as Prisma requires. A write made while one is open, through its client or the enclosing one, commits with the enclosing transaction, or, when the nested transaction rolls back to its savepoint, is reported `not-committed` and its audit rows roll back with it.
  - `$extends` called with an extension function, as `Prisma.defineExtension((client) => ...)` makes, calls the function with the audited client, so an operation the extension issues on that `client` is audited.
  - Both packages load with `require` as well as `import` on the Node.js versions their `engines` name.
  - Breaking (types): `createAuditClient` returns the type of the client it extends. The `$audit` property its type named, which the client never had, is gone.

## 0.3.0

### Minor Changes

- 86ba977: Decide whether a write is audited from the audited models it writes, and add `requireContext`.
  
  - `@kuruwic/db-audit-core` adds `auditGate`, which returns `audit` (with the audit context), `skip` or `reject` from the audit context set for a write, if any, and the audited models it writes rows of, and `AuditContextMissingError`, which an adapter throws for a rejected write. `policy()` and `WritePolicy` are unchanged; the gate runs before the write policy, and sampling does not affect it.
  - `@kuruwic/prisma-audit` adds the `requireContext` option (`boolean | ((modelName) => boolean)`, default `false`). Without an audit context, an operation that writes rows of a model in `entities` that `requireContext` holds for, nested writes included, is rejected with `AuditContextMissingError` before Prisma runs it, at any `samplingRate`. A nested `connect`, `set` or `disconnect` counts the related model only when the related rows hold the foreign key. `AuditContextMissingError` is exported from the package entry.
  - Behavior change in `@kuruwic/prisma-audit`: an operation on a model that is not in `entities` is audited when its nested writes write rows of a model that is, and those rows are now recorded. Before, the whole operation was skipped. `samplingRate` and `write.awaited` are still called with the operation's own model, which may now be one that is not in `entities`.
  - Behavior change in `@kuruwic/audit-adapter-memory`, the private reference adapter of the core: a write without an audit context now runs unaudited instead of throwing (set `requireContext` to reject it), and a write of a model that is not in `entities` no longer consults the write policy or the actor enricher.
- 7c64961: Fail the caller's operation when its audit write inside a transaction fails, and remove `write.onError`.
  
  - Fix: inside a transaction (an interactive `$transaction`, or the one `write.implicitTransaction` opens), an awaited audit-log write that failed under the default `write.onError: 'log'` was swallowed, so the operation and `$transaction` resolved with the written row. When the insert failed in the database, PostgreSQL had aborted the transaction and COMMIT rolled it back: neither the data change nor an audit row existed. InnoDB rolls a whole transaction back on a deadlock, so MySQL could lose data the same way. The library cannot tell whether a transaction survived a failed statement, so an awaited write inside a transaction that has not committed (the `immediate` write plan) now always fails the caller's operation with the write's original error, after notifying `errorObserver` under `log-write`. Use `write.awaited: false` for a model whose writes should succeed when their audit write fails.
  - A failed write after the operation has committed (awaited outside any transaction, queued until commit, or detached) and the dropped records of a committed write whose build failed never fail the operation, as before.
  - Breaking: `write.onError` is removed from `@kuruwic/prisma-audit`, and `FailureSinkConfig.writeOnError` and the `WriteOnError` type are removed from `@kuruwic/db-audit-core` and from the `@kuruwic/prisma-audit` exports. No outcome is left for them to decide.
  - Console output: without an `errorObserver`, a failure the caller cannot see (a failed write of a committed operation, or a dropped build) is logged to the console, as under the former default. With an observer, only the observer receives it. A failed write that fails the operation writes no console line. An observer that throws is logged together with the message of the failure it was given.
  - `@kuruwic/audit-adapter-memory`, the private reference adapter of the core, drops its `write.onError` option (whose default was `'throw'`). Because it always observes failures to fill `writeFailures` and `resolverFailures`, the core failure sink no longer logs its post-commit failures or dropped builds to the console.
