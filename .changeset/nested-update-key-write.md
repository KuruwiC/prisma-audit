Record a nested update that gives its row another key under the key the write gives it.

A nested `update`, the update branch of a nested `upsert` or a nested `updateMany` whose data wrote the row key of the rows it updated (the primary key, or the unique constraint of a model without one) found the rows again after the write by the key they had before it, so they were not found and not recorded, and nothing was reported.

- The rows are now found by the key the write gives them: the key they had with the key fields the data gives literal values (a value, or `{ set: value }`) replaced, as top-level batch updates already do. With `fetchBefore.update: false`, an update whose `where` names the whole row key is found the same way.
- Behavior change: a write whose data changes the key in a way its arguments do not tell (an operator such as `increment` on a key field, a relation whose foreign key is part of the key, or a nested `updateMany` with several elements of which one writes the key) is reported to the observer as `row-identification`, with `params: { path, unidentified }`. Its rows are still not recorded.
- A row key that holds the foreign key to the parent row (`@@unique([deviceCode, slot])` with `deviceCode` referencing the parent) is compared with those fields taken from the parent row as it is after the write. A row a nested `connect` moves in from another parent is recorded once, as the change of its foreign key, under its new key, instead of as a create (or not at all). A row a nested `updateMany` writes below a parent whose referenced column the same operation changes is recorded under the key `ON UPDATE CASCADE` gives it, the foreign-key change in its `changes`, and a row that change re-keys is no longer recorded as created next to a nested `create`. A nested `update` or `upsert` below such a parent names its row by the parent's new value, since Prisma writes the parent first; its read ahead of the write now names the row by the parent's value before the write, so an update is recorded with its before state and changes (it was recorded with none, and an upsert taking its update branch as a create), and a value the parent's data does not tell leaves the before state unavailable.
- Behavior change: targets at one path that their keys after the write cannot tell apart (targets naming different rows that end up with the same key, and a target naming the key another target's write gives a row) are reported as `row-identification` instead of being recorded with another row's before state.
- Behavior change: at a path holding a row whose key after the write is unknown, the rows a nested write inserts without a key the extension generated are no longer recorded as created; they are reported as `row-identification` once per inserting operation, with `params: { path, unidentified }` and a message saying they cannot be told apart from a row whose key the write changed. Rows with a key the extension generated are still recorded.
